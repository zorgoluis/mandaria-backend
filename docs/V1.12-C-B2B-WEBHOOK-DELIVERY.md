# V1.12-C — B2B Webhook Delivery

Mandaria entrega el evento que ya registró al endpoint HTTPS configurado del IntegrationClient
propietario.

```text
V1.12-B  el evento durable          (delivery.completed queda registrado)
V1.12-C  el primer intento de entrega
V1.12-D  reintentos, idempotencia y endurecimiento de seguridad
```

## 1. Qué se reutilizó

La inspección encontró que no hacía falta una segunda capa HTTP. `GoogleRoutingProvider` ya
establecía el patrón de salida server-to-server del proyecto: `fetch` global inyectable,
`AbortSignal.timeout`, clasificación de fallos en timeout / red / `HTTP_nnn`, y configuración por
`ConfigService`. V1.12-C usa exactamente ese patrón y **no** agrega `axios`, `@nestjs/axios` ni
ninguna dependencia nueva.

También se reutilizó: la superficie administrativa de `IntegrationClient` (`SUPER_ADMIN`), el patrón
de interruptores LOCAL/TEST rechazados en producción (`ROUTING_PROVIDER=local_fake`,
`MAIL_PROVIDER=local_outbox`), los guards de inmutabilidad del ledger y del Outbox, y su interruptor
de purga sólo para bases `*_test`.

No existía política SSRF previa, ni infraestructura de jobs o scheduler. Los shutdown hooks sí
estaban habilitados, y se aprovechan para drenar las entregas en vuelo.

## 2. El flujo

```text
DELIVER
  │
  ├─ transacción PostgreSQL ──▶ assignment COMPLETED + Dispatch DELIVERED + evento   (V1.12-B)
  │                              COMMIT
  │
  └─ después del commit, fuera de la transacción:
       resolver endpoint del dueño → política SSRF → POST con timeout → registrar el intento
```

**La llamada HTTP nunca está dentro de la transacción.** Un servicio se entrega aunque el cliente
esté caído, aunque no haya internet y aunque el endpoint responda 500. El primer intento se dispara
justo después de que la petición de completion fue respondida, como trabajo en segundo plano que el
servicio posee y drena en el apagado ordenado.

## 3. Configuración del destino

`B2bWebhookEndpoint`, entidad separada y no columnas en `IntegrationClient`: el estado operativo del
transporte va a crecer (suscripciones, varios destinos, políticas) y no debe ir llenando la entidad
de identidad. Un endpoint por cliente en esta versión, garantizado por `integrationClientId` único.

```
GET /api/v1/admin/integrations/{id}/webhook     (SUPER_ADMIN)
PUT /api/v1/admin/integrations/{id}/webhook     (SUPER_ADMIN)  { url, enabled? }
```

Sólo `url` y `enabled`. **No** hay `retryPolicy`, `maxAttempts`, `backoff`, cabeceras propias ni
suscripción por tipo de evento: sólo existe `delivery.completed`.

Un cliente B2B **no** configura su propio endpoint con sus credenciales. La URL decide a dónde se
conecta Mandaria desde dentro de su red, así que es un acto administrativo.

## 4. La política SSRF

La URL es entrada administrada que se convierte en una conexión saliente, así que se valida **dos
veces**: al escribirla y otra vez justo antes de cada petición, incluyendo las direcciones a las que
su nombre resuelve. Validar sólo al configurar sería teatro: un nombre público puede empezar a
resolver a una dirección privada en cualquier momento.

Se rechazan: esquemas distintos de `https`, credenciales embebidas, fragmento, más de 2048
caracteres, `localhost` y los TLD reservados (`.local`, `.internal`, `.home.arpa`), y toda dirección
que no sea unicast global — loopback, `0.0.0.0/8`, privadas (10/8, 172.16/12, 192.168/16), CGNAT
(100.64/10), link-local `169.254.0.0/16` (donde vive `169.254.169.254`), benchmarking, multicast y
reservadas, más sus equivalentes IPv6 (`::`, `::1`, `fc00::/7`, `fe80::/10`, multicast, NAT64).

Las direcciones IPv4 disfrazadas de IPv6 se deciden sobre la forma **expandida**, no sobre cómo se
escribieron: el parser de URL reescribe `[::ffff:127.0.0.1]` como `::ffff:7f00:1`, y una política
basada en expresiones regulares sobre el texto lo dejaría pasar. Ese bypass existió en la primera
versión y lo encontró una prueba unitaria.

**Redirects: nunca se siguen** (`redirect: 'manual'`). Un 3xx es un fallo de transporte. Seguirlos
es la forma más fácil de convertir una URL pública aprobada en una interna.

**Limitación conocida y deliberada:** entre la comprobación de DNS y el socket, un resolutor podría
responder distinto (DNS rebinding). Cerrarlo exige un dispatcher propio fijado a la dirección ya
validada, que es un cambio mayor del que V1.12-C debe cargar. Queda escrito, no implícito.

**LOCAL/TEST:** `B2B_WEBHOOK_ALLOW_INSECURE_TARGETS=true` admite `http` y loopback para que las
suites usen un receptor real en 127.0.0.1. **La aplicación se niega a arrancar con ese interruptor
en producción**, igual que con `local_fake` y `local_outbox`.

## 5. Lo que se envía

```http
POST /hooks/mandaria HTTP/1.1
Content-Type: application/json
x-mandaria-event-id: 5f2c…
x-mandaria-event-type: delivery.completed
```

```json
{
  "eventId": "5f2c…",
  "type": "delivery.completed",
  "occurredAt": "2026-09-25T10:15:30.500Z",
  "data": { "publicId": "MDR-000123", "externalReference": "ORDER-4711", "status": "DELIVERED",
            "execution": { "mode": "PROVIDER" }, "requestedAt": "…", "deliveredAt": "…",
            "cancelledAt": null }
}
```

El cuerpo se construye desde `B2bOutboxEvent` —las columnas y la instantánea congelada— y **nunca**
desde `DeliveryRequest` y `Dispatch` como están ahora. El nombre interno `DELIVERY_COMPLETED` no
viaja: el contrato público es `delivery.completed`, definido en V1.12-B.

`x-mandaria-event-id` es contrato: es la clave natural de deduplicación para el consumidor.

## 6. Qué cuenta como entregado

**Cualquier 2xx.** Los consumidores responden legítimamente 200, 201, 202 o 204, y exigir un código
exacto rompería integraciones sin ganar nada. Todo lo demás —incluido un 3xx— es fallo de
transporte, clasificado como `HTTP_STATUS`, `TIMEOUT`, `NETWORK` o `INVALID_ENDPOINT`.

El cuerpo de la respuesta remota se lee y se descarta. Guardarlo significaría conservar HTML
arbitrario, trazas de pila o datos personales que un sistema externo decidió devolver. Se persiste
como mucho el código de estado y una clasificación saneada y acotada a 200 caracteres.

## 7. El intento como hecho histórico

`B2bWebhookDeliveryAttempt` es una tabla aparte: el evento es el hecho y sigue siendo inmutable,
mientras que un intento de transporte es otra cosa y puede ocurrir más de una vez. No hay estados de
reintento (`PENDING`, `RETRYING`, `nextAttemptAt`): sólo `SUCCEEDED` y `FAILED`.

| Garantía | Cómo |
|---|---|
| Un intento nunca cambia | `b2b_webhook_attempt_guard` rechaza todo UPDATE; un FAILED no puede volverse SUCCEEDED ni un 500 un 200 |
| Un intento nunca se borra | El mismo guard, con el interruptor `*_test` reutilizado para las fixtures |
| El evento y el endpoint son del mismo cliente | Dos claves foráneas **compuestas**: `(eventId, integrationClientId)` y `(endpointId, integrationClientId)` |
| Un endpoint nunca cambia de dueño | `b2b_webhook_endpoint_guard` |
| Un SUCCEEDED es exactamente «respondió 2xx» | `B2bWebhookDeliveryAttempt_values_check` |

El aislamiento entre clientes es físico, no una comprobación del servicio: el endpoint se resuelve
desde la relación persistida del evento, nunca desde `externalReference`, el proveedor, el cuerpo de
la petición ni el payload.

## 8. Cambio de configuración y duplicados

Si el endpoint cambia entre el registro del evento y su entrega, se usa **el endpoint activo en el
momento del intento**, y el intento guarda la URL exacta a la que fue. Editar la configuración
después no reescribe lo que se intentó. El evento no se toca.

El contrato es **at-least-once**, no exactly-once: no se promete lo que un sistema distribuido no
puede garantizar. `eventId` permite deduplicar al consumidor, y V1.12-D construirá los reintentos
sobre estas filas.

## 9. Entrega manual

```
POST /api/v1/admin/b2b-events/{eventId}/deliver   (SUPER_ADMIN)
```

Es operacional, no un gancho de pruebas: es cómo un administrador entrega un evento cuyo primer
intento falló, mientras no existan reintentos automáticos. Hace **un** intento y responde con su
resultado. No se expuso ninguna ruta B2B para esto.

## 10. La ventana de caída

```text
COMMIT del Outbox → el proceso muere → antes del primer POST
```

V1.12-C no resuelve el reintento automático, y **no marca nada como enviado**: un evento sin
intentos es exactamente eso, un evento sin intentos. La consulta que V1.12-D necesitará —eventos sin
intento SUCCEEDED— es directa sobre estas dos tablas. Un apagado ordenado sí drena lo que está en
vuelo.

## 11. La frontera de los eventos anteriores

Desplegar V1.12-C **no** dispara los eventos ya registrados. El primer intento sólo ocurre en el
camino de completion, para entregas que suceden a partir de ahora, y la migración no hace ninguna
petición HTTP. Los eventos preexistentes quedan sin intento hasta que exista una política explícita,
o hasta que un administrador los entregue a mano uno por uno.

## 12. Lo que no hace

Sin reintentos, backoff, `nextAttemptAt`, scheduler, worker ni dead-letter. Sin HMAC ni secreto de
webhook. Sin estados de transporte más allá de `SUCCEEDED`/`FAILED`. Sin API B2B de lectura de
eventos ni administración del Outbox. Sin cambios en Mandaria Web ni en Coita Eats.

Entregar no cobra ni devuelve créditos, no toca saldos, ledger, `SERVICE_AWARD`, `SERVICE_REFUND`,
snapshots ni políticas; no recalcula rutas; no modifica el contexto de pago; y **no borra el
evento**: el Outbox sigue siendo historial durable.

## 13. Cómo se incorporará la firma (V1.12-D), sin romper el contrato

El cuerpo y las cabeceras actuales son un subconjunto estable de lo que hará falta. Una firma HMAC
se agrega como cabeceras adicionales —marca de tiempo y firma sobre el cuerpo exacto que ya se
envía— sin cambiar `eventId`, `type`, `occurredAt` ni `data`, de modo que un consumidor escrito
contra V1.12-C sigue funcionando y puede empezar a verificar cuando quiera. El secreto necesitará su
propio almacenamiento cifrado o derivado; **deliberadamente no se persiste ningún secreto ahora**,
porque guardarlo en claro para adelantar trabajo sería peor que no tenerlo.

## 14. Limitaciones conocidas

- **Un solo intento.** Un fallo queda registrado y se detiene ahí hasta V1.12-D o hasta una entrega
  manual.
- **DNS rebinding** entre la validación y el socket, descrito arriba.
- **Sin firma:** un receptor no puede verificar todavía que la petición viene de Mandaria. Debe
  tratar el webhook como una señal para consultar `GET /delivery-requests/{publicId}/status`, que
  sigue siendo la fuente autenticada.
- **Concurrencia:** dos procesos podrían entregar el mismo evento a la vez. Cada intento tiene
  identidad propia y ambos quedan auditados; el Outbox no se corrompe. No se construyó un lease
  distribuido para V1.12-C.
- **Sin retención:** los intentos se acumulan como historial.

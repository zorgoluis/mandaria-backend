## Persistencia y autorización

No se editaron migraciones anteriores. `DeliveryLocationHead` conserva un solo slot por MDR, ligado operativamente a la asignación vigente mediante locks y triggers; ninguna lista de posiciones. `DeliveryTrackingLinkHead` conserva un enlace vigente y un recibo acotado. `LocationRateBucket` contiene contadores compartidos PostgreSQL con caducidad.

Transferencia/reasignación/incidencia/terminal eliminan muestra, fingerprint y fechas de la muestra, retiran stream y avanzan versiones. Coordenadas finitas, rango geográfico; precisión >0 y <=100m. Una captura futura tolerada usa recepción como máximo para calcular frescura. Duplicado exacto conserva versión; mismo número con contenido distinto:409; secuencia inferior/purgada:SUPERSEDED, sin reinserción.
- Cambiar flag GPS invalida el stream y aumenta su revisión/versiones mediante `trackingEnabled` persistido. **No ejecutar instancias con configuraciones diferentes.** Reiniciar con la misma política conserva la muestra/stream válidos; la app debe reconciliar antes de publicar. Las cuotas no se reinician al reiniciar Node.

## Lectura coherente y tiempo

La fotografía logística y GPS se obtiene dentro de una transacción RepeatableRead con reintentos limitados de serialización. Titular ve desde TO_PICKUP; destinatario desde PICKED_UP. Incidencia abierta oculta coordenadas y muestra atención; legacy nunca fabrica fase/posición; sin asignación se devuelve explícitamente NONE. Terminal retira GPS.

`publicVersion` ordena progreso; `locationVersion` ordena el objeto `location` por MDR/audiencia; `assignmentGeneration` es una generación opaca monotónica de invalidación, **no cuenta asignaciones**. Comparar cadenas como BigInt. La hora de evaluación/frescura está separada en `observation`; no provoca una escritura cada segundo. No reutilizar caché de otra audiencia.

Hasta 60s inclusive:RECENT; después:STALE; a600s no se entregan coordenadas. Las comparaciones SQL usan UTC explícito, independientemente del timezone de sesión. La lectura purga la muestra vencida de forma durable. Sin lectores, un worker cada30s procesa hasta500 muestras/500 hashes/500 buckets por ciclo: no se promete borrado físico al milisegundo600 si hay cola o caída del worker. `LOCATION_CLEANUP_FAILED` y `LOCATION_SAMPLES_ERASED` registran sólo evento/conteo; supervisarlos. Una muestra tardía no rejuvenece al llegar.

Sobrescritura/purga afecta **datos vivos**; no borra WAL, réplicas o backups. Retención/acceso de coordenadas en backups pendiente del propietario. No se construye historial con copias. El diseño ya definía purga viva: se implementa con lectura fail-closed y limpieza acotada; no se inventa una retención de backups.

## Enlace y recuperación

Se emite únicamente tras aceptación, mientras OPEN/ASSIGNED. Selector aleatorio128bits y secreto256bits; PostgreSQL guarda SHA-256 con separación de dominio, nunca token/URL completos. Comparación de hash con timingSafeEqual. URL WEB `/track#t=selector.secret`; API constante usa `Authorization: Tracking selector.secret`.

TTL absoluto24h desde emisión. Terminal deja estado sin GPS hasta `min(expiresAt, terminalOutcome.occurredAt + 1h)`; en la frontera se devuelve404. Consultar no renueva. Revocar retira hash de inmediato. Worker elimina hashes tras TTL/gracia. Suspensión de propietario impide lectura compartida. La revocación de una credencial B2B por sí sola no revoca el enlace independiente; revocar enlace explícitamente.

ISSUE inicial:201 con `url` y `secretAvailable:true`; replay del último recibo propio:200, sin URL y `secretAvailable:false`. Consultar intento conserva actor (User o credential B2B), propietario, MDR, operación, clave hasheada y revisión original. No necesita formulario ni devuelve secreto.

| Resultado | Interpretación |
|---|---|
| APPLIED_SECRET_UNAVAILABLE | Se emitió ese intento; secreto irrecuperable. Consultar enlace actual y revocar/sustituir con confirmación. |
| APPLIED_REVOKED | Ese intento de revocación aplicó; consultar metadata actual por si hubo otro enlace posterior. |
| PENDING_OR_UNKNOWN | Misma revisión sin recibo del intento; mantener bloqueo. Ausencia no prueba fracaso. |
| SUPERSEDED | Revisión avanzó y el recibo acotado ya no acredita ese intento. El POST con la revisión original no puede aplicar después. No significa que jamás aplicó ni que el enlace actual esté revocado. |

El cierre técnico es el POST `/revoke` con revisión actual, UUID nuevo y confirmación. Avanza revisión incluso sin enlace. Si gana frente al ISSUE original, el tardío falla409; si ISSUE gana, revoke con revisión anterior falla409. GET nunca cierra. No reemitir automáticamente tras timeout. Recibos contienen resultado histórico seguro; consultar metadata para estado vigente. No hay registro ilimitado de todos los intentos.

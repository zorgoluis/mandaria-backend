## Alcance y contrato

Se reutiliza `POST /api/v1/delivery-quotes/:publicId/accept` con Integration Bearer y `quotes:accept`. Una MQ convertida requiere Idempotency-Key ASCII visible de 8–255 caracteres y:

```json
{
  "customerAuthorization": {
    "version": 1,
    "status": "AUTHORIZED_BY_CUSTOMER",
    "reference": "consent-demo-101",
    "authorizedAt": "2026-09-29T05:01:00.000Z",
    "quotePublicId": "MQ-000101",
    "amount": "25.00",
    "currency": "MXN",
    "expiresAt": "2026-09-29T05:15:00.000Z"
  }
}
```

Ejemplo sintético de forma; no es una solicitud operable. La atestación debe coincidir con identidad, importe, moneda y vencimiento persistidos; `MQ.createdAt <= authorizedAt <= acceptedAt DB < expiresAt`. Fechas normalizadas a UTC milisegundos, precio string con dos decimales. Identidad/expiración técnica nunca vienen del body. Coita conserva evidencia original; Mandaria **no verifica directamente el consentimiento humano**.

200 inicial/replay, proyección Quote existente, `Idempotent-Replayed: false/true`, `Cache-Control: no-store` y correlación existente `X-Request-Id`. Sin referencia privada, IDs de credencial ni expiración técnica en respuesta. `/integrations/me` mantiene su proyección pública explícita al ampliar el principal interno.

Legacy CASH/COURIER_ADVANCE conserva aceptación sin body o con `{}`, sin key obligatoria y replay previo. Atestación enviada a legacy → 400 `AUTHORIZED_ACCEPT_ORIGIN_REQUIRED`; DTO inválido/extras o falta de key/atestación convertida → 400 `VALIDATION_ERROR`. Esta última respuesta reemplaza la barrera HTTP B `AUTHORIZED_ACCEPT_REQUIRED` para llamadas vacías; SQL y llamadas internas legacy sin evidencia siguen bloqueadas. Pruebas B2/B4 actualizan **sólo** esa expectativa de contrato; no se omiten escenarios.

Errores de creación C: `CUSTOMER_AUTHORIZATION_MISMATCH`, `QUOTE_ALREADY_AUTHORIZED`, `QUOTE_NOT_ACCEPTABLE`, `QUOTE_EXPIRED`, `AUTHORIZED_ACCEPT_SERVICE_UNAVAILABLE` (409); key incompatible conserva `HTTP_409`. Flag apagado → 503 `AUTHORIZED_ACCEPT_DISABLED`; timeout/conflicto transaccional reconocido → 503 `AUTHORIZED_ACCEPT_UNAVAILABLE`. Auth inválida se mantiene genérica 401; scope ausente 403; ajeno/inexistente 404. Errores de créditos existentes conservados. No se convierte todo error SQL en conflicto/replay.

## Transacción e integridad

- Registro `AuthorizedQuoteAcceptance` inmutable: conversión/MDR/MQ/integración, key, credencial real, expiración técnica validada, tuple atestiguado, tiempo DB e ID Dispatch preasignado. No autorización PENDING ni backfill.
- Migración incremental [20260929000100](../prisma/migrations/20260929000100_authorized_quote_acceptance/migration.sql). Índices únicos, FKs compuestas y FK Dispatch diferida. No se edita historia de migraciones.
- `IdempotencyService.execute` existente: key + evidencia + MQ ACCEPTED + Dispatch + snapshots en una transacción. Fallos de publicación revierten todo. Sin routing, consumo A5, nueva tarifa o SERVICE_AWARD durante accept.
- Locks: key → integración SHARE → credencial SHARE → MDR UPDATE → MQ SHARE → zona SHARE → políticas existentes. Administración que bloquea dos identidades mantiene padre→credencial; revocación simple bloquea sólo credencial, suspensión sólo padre. Cancelación serializa sobre MDR. Completion serializa sobre Dispatch. La revalidación ocurre después de esperas y nuevamente en constraints de creación.
- Sólo nuevas aceptaciones comprueban flag y vigencia. Replay exacto recupera mismos vínculos incluso vencida/cancelada o flag apagado, con autenticación vigente; no reabre. Diferentes keys para la misma MQ: un ganador, las demás sin key persistida.
- Barreras B de manifiesto, snapshot, TTL, hijos, ownership y recotización permanecen. Se sustituye sólo bloqueo absoluto de ACCEPTED/Dispatch por evidencia exacta. La apertura consulta evidencia persistida; no hay skipGuard ni bandera que supla consentimiento.
- SQL impide evidencia/key huérfanos, tuple/relaciones falsos, adopción de Dispatch previo y edición/borrado de evidencia/key. Lifecycle histórico no revalida credencial/TTL originales. Guardas económicas/snapshots/refunds/outbox continúan aplicando.

**Límites:** SQL verifica integridad, no firma JWT ni acto humano. La expiración técnica proviene del backend autenticado. Un escritor con capacidad de fabricar el conjunto completo puede atestiguar falsamente; DDL/superusuario quedan fuera. Constraints diferidos comprueban tiempo al evaluarse, no el instante físico del commit; SQL directo puede adelantar evaluación con SET CONSTRAINTS IMMEDIATE. No se usa ese mecanismo en HTTP. Flag por proceso no revoca transacciones globalmente de forma instantánea.

## Recuperación, comida y operación

Cancelar admite MDR convertida con MQ vencida; conserva MPQ consumida y snapshot. **200 cancel/MDR CANCELLED no garantiza ausencia de entrega:** si completion ganó, status público sigue DELIVERED. Antes de reemplazar, Coita debe:

1. Frenar acciones de la generación antigua y reconciliar respuestas inciertas con las mismas keys.
2. Confirmar MDR propia CANCELLED y cancelledAt mediante cancel200 o GET detalle.
3. Obtener después GET `/delivery-requests/:publicId/status`: CANCELLED/EXPIRED y deliveredAt null. DELIVERED, estado contradictorio, error o incertidumbre impiden reinicio.
4. Persistir cierre, comprobar pedido vigente y conservar confirmación verdadera del restaurante. Emitir nueva MPQ, convertir vigente y obtener nuevo consentimiento sobre la nueva MQ exacta antes de aceptar. No reutilizar consentimiento aunque baje el precio ni renovar TTL.

No se añade sustitución enlazada ni unicidad sobre externalReference. Coita debe serializar sus generaciones/entradas por pedido; esta coordinación externa no se implementa aquí. Reiniciar envío no exige otra transferencia de comida ni implica reembolso. PREPAID es comida pagada, no envío cobrado. Adelanto legacy, precio/envío y créditos del ejecutor permanecen separados; accept y DELIVERED no acreditan cobro. Refunds de créditos existentes se conservan.

# V1.13-D — Instrucciones financieras para ejecutores

Fecha: 2026-09-29. Base: `9785ee1`, rama `1.13-Precotización_integración_comida_prepagada`, paquete 1.12.0 sin cambio.

## Alcance y fuentes

Proyección aditiva de instrucciones para conversiones PREPAID con aceptación autorizada. Reutiliza `Dispatch.deliveryQuote` ACCEPTED para importe/moneda, `PrequoteConversion` para la instrucción persistida y su declaración de comida pagada, y la existencia de `authorizedAcceptance` para distinguir este origen. No calcula ni guarda otro precio. PREPAID se refiere a **comida**, no a envío pagado.

La declaración del integrador sobre comida pagada al restaurante no es una verificación bancaria de Mandaria. La aceptación de MQ acredita la atestación de Coita sobre autorización del cliente; no confirma cobro. DELIVERED sólo confirma entrega física, tampoco cobro.

Referencias acotadas: [diseño C1](V1.13-C1-AUTHORIZED-ACCEPTANCE-DESIGN.md), [implementación C2](V1.13-C2-AUTHORIZED-ACCEPTANCE-IMPLEMENTATION.md). C4 conserva **PARTIAL**; esta implementación no retoma su diagnóstico, lo cierra ni activa el flujo. Pendientes operativos de A intactos.

## Contrato exacto

Campo opcional `collectionInstructions`, omitido en legacy (incluido PREPAID no convertido). Propiedades:

| Campo | Fuente y significado |
|---|---|
| `applicability` | `OFFER`, `CURRENT` o `HISTORICAL`, derivados del estado actual y de la vista autorizada |
| `goodsPaidToRestaurant` | `true`: declaración persistida CONFIRMED_BY_MERCHANT |
| `advanceToRestaurant` | `false`: ningún adelanto al restaurante |
| `collectGoodsFromRecipient` | `false`: ningún cobro de comida al destinatario |
| `deliveryFee.amount` | Decimal string con dos posiciones, exactamente MQ aceptada; sin conversión a float |
| `deliveryFee.currency` | Moneda de esa MQ |
| `payer` | `RECIPIENT`, de la instrucción persistida |
| `method` | `CASH`, de la instrucción persistida |
| `dueAt` | `DELIVERY`, de la instrucción persistida |
| `component` | `DELIVERY_FEE`, de la instrucción persistida |

Extracto **real** capturado por la prueba local de claim (datos sintéticos):

```json
{
  "collectionInstructions": {
    "applicability": "CURRENT",
    "goodsPaidToRestaurant": true,
    "advanceToRestaurant": false,
    "collectGoodsFromRecipient": false,
    "deliveryFee": { "amount": "25.10", "currency": "MXN" },
    "payer": "RECIPIENT",
    "method": "CASH",
    "dueAt": "DELIVERY",
    "component": "DELIVERY_FEE"
  }
}
```

[Respuesta HTTP completa capturada](checks/v1.13-d-response-example.json). Los 150.00 de comida del fixture y el costo en créditos permanecen separados de los 25.10 de envío.

### Endpoints existentes que incorporan el campo

Todas las rutas tienen prefijo `/api/v1`. `:id` representa `dispatchId`. No se crean endpoints, permisos ni scopes.

| Superficie | Rutas | Ubicación |
|---|---|---|
| Proveedor | GET `/provider/dispatches`, GET `/provider/dispatches/:id` | `items[].collectionInstructions` / `collectionInstructions` |
| Proveedor, ejecución | POST `/provider/dispatches/:id/claim`, `/release`, `/deliver` | `collectionInstructions`, cuando la vista permite detalle |
| Asignación de flotilla | POST `/provider/dispatches/:id/assignment`, `/assignment/reassign`, `/assignment/cancel` | `collectionInstructions`, junto al `paymentContext` existente |
| Independiente | GET `/driver/dispatches/available`, GET `/driver/dispatches/:id` | `items[].collectionInstructions` / `collectionInstructions` |
| Independiente, ejecución | POST `/driver/dispatches/:id/take`, `/release`, `/deliver` | `collectionInstructions` |
| Repartidor humano, flotilla o independiente | GET `/driver/me`, PATCH `/driver/availability` | `activeDeliveryAssignment.collectionInstructions` |

GET del historial de asignaciones no se amplía. Vista SUMMARY del proveedor no expone instrucciones ni precio. No se cambian las proyecciones B2B ni administrativas. Persisten los guards humanos, membership del proveedor y ownership/elegibilidad del independiente. Un token B2B no obtiene acceso a estas rutas.

### Vigencia y ciclo operativo

- **OFFER:** solicitud CREATED, Dispatch OPEN efectivo y vista de oferta. Condiciones para decidir tomar el servicio; **no autorizan a cobrar**. Una oferta vencida no conserva esa vigencia.
- **CURRENT:** solicitud CREATED, Dispatch CLAIMED y vista del ejecutor vigente. Instrucción de cobrar únicamente al entregar, no en la aceptación ni en pickup.
- **HISTORICAL:** cancelación, expiración, entrega o asignación terminada. Conserva importe y condiciones como referencia; nunca solicita un cobro ni afirma que se haya realizado.
- Reasignación: respuesta nueva CURRENT; el repartidor anterior ya no tiene asignación activa. Cancelar una asignación devuelve HISTORICAL; no extingue por sí mismo el claim del proveedor.
- Release: el proveedor pasa a SUMMARY y pierde el campo. El independiente recibe OFFER si el Dispatch vuelve a OPEN; no es CURRENT ni permite cobrar o volver a tomarlo. No se altera esta política existente. `/driver/me` deja de tener asignación activa.
- Cancelar MDR después de entregar conserva DELIVERED; la instrucción sigue HISTORICAL. No se fabrica estado de pago.
- Ninguna lectura garantiza vigencia futura frente a una cancelación concurrente. Frontend debe refrescar estado, invalidar caché al mutar y retirar acciones al perder asignación/ownership o ante error de autorización.

- Helper puro y selección Prisma explícita en `src/delivery-assignments/collection-instructions.ts`; esquema Swagger compartido en `collection-instructions.responses.ts`.
- Reutilización en `dispatch.select.ts`, `independent-dispatch.select.ts`, `DeliveryAssignmentsService.withPaymentContext` y `DriversService.self`; DTOs de respuesta correspondientes actualizados.
- El helper no lee referencias privadas del restaurante, referencia de consentimiento, IDs de credenciales ni cuerpos de auditoría. Sólo usa un marcador interno de aceptación; tampoco lo devuelve.
- Se conserva el `paymentContext` previo y los cálculos CASH/COURIER_ADVANCE. No cambian TTL, idempotencia, aceptación, cancelación/completion ni crédito/refund; sólo selects y respuestas.
- Sin tablas, migraciones, versión, flags nuevos, .env o configuración operativa. Los flags de pruebas se habilitan únicamente dentro de sus procesos locales; no activación.

## 3. Tiempo y SET CONSTRAINTS IMMEDIATE

Se ejercitaron tres variantes con SQL real y guardas activas:

1. **Antes de construir:** `SET CONSTRAINTS ALL IMMEDIATE` hace fallar la key aún sin resultado. Rollback; no abre una ruta de construcción parcial.
2. **Después de construir completamente:** constraints inmediatas aceptan el conjunto. INSERT extra, modificación de manifiesto/snapshot y DELETE de contexto siguen bloqueados. SAVEPOINT/ROLLBACK TO permite continuar y comprometer únicamente el conjunto válido.
3. **Validar antes, esperar a después de expiresAt y commit:** el escritor directo puede comprometer una conversión ya vencida. La espera se calcula con `expiresAt` y `clock_timestamp()` nativos PostgreSQL. Se confirma reloj DB posterior, expiry original intacto, MPQ consumida una sola vez y prohibición de ACCEPTED/Dispatch.

**Distinción de garantías:** HTTP deja las constraints diferidas y revalida antes de construir y al final. SQL protege integridad estructural sin depender del instante de evaluación. Un escritor directo puede adelantar la comprobación temporal, pero no ampliar expiry, reutilizar MPQ ni habilitar despacho. B1/B2 ya documentaban este límite y no prometen commit físico anterior al vencimiento. No se clasifica como defecto bajo ese contrato. Si se exige prohibir todo commit tardío directo, requiere una decisión arquitectónica explícita, no una relajación/corrección silenciosa en B3.

La igualdad exacta del reloj se prueba determinísticamente en la unitaria existente reejecutada. Las pruebas PostgreSQL prueban antes/después y el cruce por lock/escrituras; no se afirma sincronización física al mismo milisegundo. No se probó wraparound XID: el manifiesto no depende de XID.

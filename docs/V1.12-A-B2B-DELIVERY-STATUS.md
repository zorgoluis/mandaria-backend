# V1.12-A — B2B Delivery Status

Estado logístico de una DeliveryRequest, para el IntegrationClient que la creó. Sólo lectura.

## 1. Pregunta que responde

Hasta V1.11-A un cliente B2B podía crear una solicitud, cotizarla, aceptarla y cancelarla, pero no
podía saber si se entregó. El cierre operativo existía (`DELIVERED`) y era invisible desde afuera.
V1.12-A abre esa lectura y **nada más**: no notifica, no reintenta, no publica eventos.

## 2. Endpoint

```
GET /api/v1/delivery-requests/{publicId}/status
```

Token B2B con scope `deliveries:read`. El IntegrationClient sale del token, nunca del path ni del
body. Una solicitud de otro cliente responde **404**, exactamente igual que una inexistente.

Respuesta:

```json
{
  "publicId": "MDR-000123",
  "externalReference": "ORDER-4711",
  "status": "DELIVERED",
  "execution": { "mode": "PROVIDER" },
  "requestedAt": "2026-09-23T18:04:11.000Z",
  "deliveredAt": "2026-09-23T18:52:40.117Z",
  "cancelledAt": null
}
```

## 3. Estados públicos

Seis, estables, definidos por el contrato y no por el modelo interno:

| Estado | Significado para el cliente |
|---|---|
| `REQUESTED` | La solicitud existe; todavía no se publicó ningún servicio. |
| `OPEN` | El servicio está publicado y espera a quien lo tome. |
| `ASSIGNED` | Alguien se adjudicó el servicio y lo está ejecutando. |
| `DELIVERED` | Se entregó. Terminal. |
| `CANCELLED` | Se canceló antes de entregar. |
| `EXPIRED` | Nadie lo tomó dentro de su ventana. |

`execution.mode` vale `PROVIDER` o `INDEPENDENT`, o es `null` mientras nadie se lo adjudicó. Es lo
único que el cliente sabe de quién ejecuta: no se publican Driver, Vehicle, proveedor, créditos,
políticas, snapshots ni identificadores internos.

## 4. Traducción desde el dominio real

La correspondencia vive en **un solo lugar**, `src/deliveries/delivery-status.ts`, y reutiliza
`effectiveDispatchStatus` de V1.7 para que la caducidad perezosa se lea igual que en el resto del
sistema (un `OPEN` cuya ventana ya cerró se informa `EXPIRED` aunque todavía no se haya persistido).

| Estado interno | Estado público |
|---|---|
| Sin Dispatch, DeliveryRequest `CREATED` | `REQUESTED` |
| Sin Dispatch, DeliveryRequest `CANCELLED` | `CANCELLED` |
| `Dispatch.OPEN` dentro de su ventana | `OPEN` |
| `Dispatch.OPEN` fuera de su ventana | `EXPIRED` |
| `Dispatch.CLAIMED` | `ASSIGNED` |
| `Dispatch.DELIVERED` | `DELIVERED` |
| `Dispatch.CANCELLED` | `CANCELLED` |
| `Dispatch.EXPIRED` | `EXPIRED` |

Decisiones que la tabla no dice sola:

- **El Dispatch manda sobre la DeliveryRequest.** Un servicio entregado sigue leyéndose `DELIVERED`
  aunque después se cancele la solicitud, porque la entrega ya ocurrió y `DELIVERED` es irreversible.
- **La asignación interna no es un estado público.** Que el proveedor elija Driver y Vehicle (V1.8)
  o los reasigne no cambia nada afuera: sigue siendo `ASSIGNED`. Se evitó así publicar un detalle
  que el cliente no puede usar y que ataría la API a la operación interna del proveedor.
- **`execution` no es pegajoso.** Si el proveedor libera el servicio (y V1.10-E le devuelve sus
  créditos), la lectura vuelve a `OPEN` con `execution: null`.
- **No se inventaron estados operativos nuevos.** Se inspeccionó el dominio antes de escribir código
  y `DispatchStatus` ya cubría todo lo observable; recogido, en camino o intento fallido no existen
  internamente y habría sido mentir publicarlos.

## 5. Sin migración

No se agregó ni modificó ninguna columna, tabla, índice, constraint o trigger. Todo lo que la
respuesta necesita ya estaba: `publicId`, `externalReference`, `requestedAt`, `cancelledAt`,
`Dispatch.status`, `expiresAt`, `claimedByProviderId`, `claimedByIndependentDriverId`,
`deliveredAt` y `cancelledAt`. El `select` de Prisma trae exactamente esos campos y ninguno más.

## 6. Mandaria sigue siendo la única autoridad logística

El cliente B2B **no** marca entregas, no reclama, no asigna y no libera. La ruta es `GET` y no
existe ninguna otra forma de tocar el estado: `POST`, `PUT`, `PATCH` y `DELETE` sobre la misma ruta
responden 404, y las rutas operativas de proveedor y repartidor rechazan un token B2B con 401.

Leer no tiene consecuencias: no mueve saldos ni ledger, no toca el Dispatch ni la asignación, no
llama al proveedor de routing, no recalcula políticas ni snapshots y no emite eventos de auditoría.
Es apto para sondeo periódico.

## 7. Aislamiento

Un `publicId` ajeno y uno inexistente producen la **misma** respuesta 404 (`Delivery request not
found`), byte a byte salvo el `timestamp` y el `path` que el propio llamante envió. No hay forma de
distinguir «existe pero no es tuyo» de «no existe», así que los identificadores no se pueden sondear.

## 8. Fuera de alcance

Sin webhooks, sin Outbox, sin reintentos, sin tracking ni GPS, sin estados intermedios de ejecución,
sin histórico de transiciones (el cliente ve el estado actual, no la línea de tiempo), sin
notificaciones push y sin cambios en Mandaria Web ni en Coita Eats.

## 9. Limitaciones conocidas

- **Sondeo, no notificación.** Enterarse de una entrega exige consultar; un cliente que no consulte
  no se entera. Es justamente lo que resolvería V1.12-B con webhooks.
- **Sin línea de tiempo.** No se publica cuándo pasó a `OPEN` ni cuándo a `ASSIGNED`; sólo
  `requestedAt`, `deliveredAt` y `cancelledAt`.
- **`EXPIRED` perezoso.** Un `OPEN` vencido se informa `EXPIRED` aunque la fila siga diciendo
  `OPEN`; es coherente con el resto del sistema, pero significa que la lectura pública puede ir por
  delante de la fila persistida.
- **La entrega es una declaración.** `DELIVERED` refleja lo que el actor que ejecutó el servicio
  afirmó en V1.11-A; Mandaria no lo verifica (sin foto, firma, OTP ni GPS).

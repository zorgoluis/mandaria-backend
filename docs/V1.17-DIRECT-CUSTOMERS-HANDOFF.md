## 1. Convenciones propuestas

Base de rutas `/api/v1`. Se indican paths relativos; no fijar un nuevo dominio desde este documento. Humanos: JWT User actual y futuro CustomerGuard; nunca clientSecret en Web/App. CUSTOMER no se envía desde registro ni habilita rutas de operaciones. Perfiles anexados a un User DRIVER/PROVIDER_ADMIN conservan ese rol, pero requieren seleccionar contexto cliente y se autorizan por CustomerAccount.

Todos los DTO rechazan campos desconocidos. Importes decimales como string, moneda y precios calculados por Mandaria; fechas UTC ISO8601; referencias públicas MDR/MPQ/MQ. Owner, actor, timestamps de registro y cupo se determinan en backend. Paginación humana propuesta page/pageSize con validadores existentes; no inventar otro formato. Error usa el envelope actual (`statusCode`, `code`, `message`, `path`, `timestamp`, correlación si disponible); códigos nuevos marcados abajo como propuestos.

Idempotency-Key: reutilizar validación visible ASCII8–255, namespace por propietario; nunca nueva clave automática después de timeout de creación/conversión/aceptación. Misma clave y mismo input recupera resultado; conflicto de payload409. Igual clave de otro propietario no revela ni recupera recursos ajenos. No serializar tokens ni bodies privados en logs o marcadores UI.

Diferencias: resend requiere perfil completo; confirm/reset devuelven CONFIRMED (201/200); perfil expone active sin capacidades; change-type y capabilities continúan pendientes. Se agregaron las dos rutas de verificación de contacto.

Perfil propuesto: `{type,displayName,businessName,revision,status,emailVerified}` sin hashes ni tokens. No publicar identificador interno de cuenta como capacidad de acceso. Error401 por sesión,403 por perfil suspendido/no verificado;404 por recurso ajeno;409 PROFILE_ALREADY_EXISTS, CUSTOMER_ACTIVE_REQUESTS o PROFILE_REVISION_CONFLICT (propuestos). ## 3. Cotizar, solicitar y confirmar — propuestas directas

Recomendación: un único recorrido principal MPQ→MDR+MQ→aceptación. No abrir un segundo POST MDR directo sin MPQ en V1.17; la solicitud sin cotización es estado heredado/posible en otros canales, no motivo para duplicar rutas humanas. Múltiples cotizaciones previas permitidas bajo límites de consumo, pero PERSONAL sólo convierte una a la vez.

| Método/ruta propuesta | Entrada / validación | Respuesta |
|---|---|---|
| POST `/customer/delivery-prequotes` | condiciones de servicio/paradas geométricas/paquetes existentes + `shippingPayer?`; key obligatoria |201 MPQ;200 replay; precio/TTL/términos inmutables, no cupo reservado |
| GET `/customer/delivery-prequotes/:publicId` | owner de sesión |200 MPQ y vínculos MDR/MQ propios si convertida;404 ajeno |
| POST `/customer/delivery-prequotes/:publicId/convert` | `{conditionsVersion,shippingTermsVersion,deliveryRequest,payerContact}` + key |201 conversión/MDR+MQ;200 replay. Cupo, propietario, términos, precio y vencimiento en misma transacción |
| GET `/customer/delivery-requests` | page/pageSize, publicId/status y rango temporal validados |200 lista propia; no filtro de integrationClientId/customerAccountId |
| GET `/customer/delivery-requests/:publicId` | referencia propia |200 detalle autorizado, MQ actual, términos y acciones; no datos administrativos |
| GET `/customer/delivery-requests/:publicId/status` | referencia propia |200 fotografía/publicVersion, estado/asignación/progreso/resultado; no contacto privado en fotografía compartible |
| GET `/customer/delivery-requests/:publicId/quotes` | referencia propia |200 cotizaciones propias; precio exacto, vigencia y términos |
| GET `/customer/delivery-quotes/:publicId` | owner via MDR |200 MQ;404 ajena |
| POST `/customer/delivery-quotes/:publicId/accept` | `{authorization:{quotePublicId,amount,currency,expiresAt,shippingTermsVersion,shippingTermsHash,accepted:true}}` + key |200 aceptación/estado y referencia Dispatch sólo si pública existente; no ID interno nuevo. Reutiliza accept/openDispatch transaccionales |
| POST `/customer/delivery-requests/:publicId/cancel` | `{reason}` + key recomendada |200 estado/resultado actual; no garantía por respuesta de MDR aislada. Idempotente, original razón/fecha preservadas |

Usuario/fecha de autorización directa los registra servidor, no campos elegibles por cliente. El JSON propuesto de autorización no sustituye el B2B `customerAuthorization` actual: canales distintos. Directo confirma por su sesión; no se guarda una falsa referencia de restaurante.

`deliveryRequest` conserva layout validado de stops1:PICKUP/2:DROPOFF, packages y financialContext actuales; dirección y contactos definitivos están en conversión, no MPQ geométrica. El servidor verifica que las condiciones tarifadas no cambiaron. Extensión DIRECT de conversión debe validar modos de mercancía soportados sin copiar restricciones de confirmación mercantil B2B. PREPAID de mercancía no marca pagado el envío.

`payerContact`: `{name,phone,capacity:REQUESTER|AUTHORIZED_REPRESENTATIVE}` para REQUESTER; la designación se confirma en formulario, no se deduce de stops[0].contactName. Para RECIPIENT se reutiliza contacto de destino cuando el negocio lo confirme; no aceptar cambios después de congelar sin nueva secuencia/consentimiento. Sin identificación civil ni nuevos archivos.

### Errores nuevos propuestos y recuperación

| HTTP/código | Acción cliente |
|---|---|
|400 SHIPPING_PAYER_NOT_ALLOWED | PERSONAL intentó RECIPIENT o B2B override; corregir input, no ocultar el error |
|409 PERSONAL_ACTIVE_REQUEST_EXISTS | Mostrar MDR propia ocupante; recuperar/cancelar legalmente esa solicitud |
|409 SHIPPING_POLICY_CHANGED / SHIPPING_TERMS_MISMATCH | No conversión parcial. Solicitar nueva MPQ/términos, obtener consentimiento; no cambiar pagador silenciosamente |
|409 IDEMPOTENCY_CONFLICT | Key usada con otra operación/payload; investigar intención. No reintentar automáticamente con nueva key |
|409 CUSTOMER_ACTIVE_REQUESTS / PROFILE_REVISION_CONFLICT | Refrescar perfil/cupo; no forzar cambio de tipo |
|409 PREQUOTE_ALREADY_CONVERTED / PREQUOTE_EXPIRED | Reconciliar MPQ; reutilizar MDR/MQ ya creadas si corresponde; no crear sucesor mientras estado incierto |
|409 CUSTODY_OPERATION_FORBIDDEN / CUSTODY_INCIDENT_OPEN (existentes) | No cancelar físicamente ni crear reemplazo; conservar MDR y escalar custodia |
|429 /503 /red | Backoff y Retry-After cuando exista; conservar intento, consultar/repetir misma key. No duplicar solicitudes |

Tras timeout: si hay MPQ, GET muestra conversión única y referencias; si no se recibió MPQ, repetir emisión con misma key/input usando reserva durable existente adaptada. Tras accept, consultar MQ/MDR/status y repetir misma key si corresponde. Un GET sin resultado no demuestra que POST retrasado no llegará; no abandonar el marcador y cambiar key. Para abandonar una intención aún incierta debe existir cancelación final de su recurso o cierre explícito del recibo bajo locks compartidos (propuesto cuando el recibo permita tal operación); nunca un GET con efectos ni borrado de clave. Cancelar MDR protege contra accept tardío: ambos comparten locks y estado terminal. Cancelar no reembolsa comida.

Si MQ vence después de conversión: cancelar MDR anterior y acreditar terminal sin custodia; nueva MPQ, conversión y consentimiento/aceptación de MQ nueva. No ampliar TTL, reabrir solicitud cerrada ni mover pagos entre pedidos por inferencia. PERSONAL recupera cupo sólo al commit del cierre.

## 4. B2B — compatibilidad y extensiones propuestas

Las rutas actuales MPQ/MDR/MQ conservan método/ruta y scopes de los controllers; ninguna regla de cupo personal entra en IntegrationGuard. GET `/integrations/me` puede añadir `shippingPolicy:{defaultPayer,revision,supportedCombinations}` de la propia integración sin añadir scope administrativo. Propuesta, no presente hoy.

### Administración de configuración (NO IMPLEMENTADA)

`GET /admin/integrations/:id/shipping-policy` →200 política, revisión y fecha; `PATCH` en esa ruta con `{defaultPayer:REQUESTER|RECIPIENT,expectedRevision}` y key →200 nueva política. Exclusivamente AccessGuard+SUPER_ADMIN; JWTB2B403/401 según guard vigente. ID UUID validado,404 integración ausente,409 revisión desactualizada; auditoría actor/antes/después. Conservar PATCH integración original de status/204, no cambiarlo a setters arbitrarios.

No permitir scopes B2B autoeditables para cambiar pagador. No override en creación MDR/conversión. El eco de instrucciones que ya envía convert debe coincidir con términos, no decidirlos.

### Extensiones de respuesta/input B2B a revisar

- MPQ: snapshot seguro `shippingPayment` sin contactos; origen de política/revisión para conocer cambios, no valores secretos. MDR/detail/status: pagador efectivo de snapshot, nunca default actual. PublicVersion cambia cuando cambie la representación.
- Conversión: aceptar nueva combinación REQUESTER/CASH/PICKUP sólo si coincide con política/snapshot y soporte habilitado. Contacto pagador/representante privado en input/detail autorizado; no se publica en status/webhook. RECIPIENT/CASH/DELIVERY y body antiguo siguen soportados con default histórico.
- Aceptación autorizada v2: MQ/precio/TTL y eco exacto termsVersion/hash; credential sigue siendo B2B. Versión1 se conserva para términos históricos RECIPIENT, no sirve para afirmar consentimiento REQUESTER desconocido.
- `delivery.completed` no incorpora datos del pagador ni altera sobre/firma/reintentos; consultar GET para términos/resultado. Mantener propiedad B2B y congelación del payload.

Portal B2B: mantener la allowlist explícita de métodos/rutas. Rutas de Customer, registro/reset y futura admin shipping-policy pertenecen a contrato humano/interno, no al OpenAPI B2B descargable. Sólo ampliar schemas/op existentes revisadas, o agregar nueva operación B2B mediante aprobación explícita. La implementación A regeneró ambos artefactos; las adiciones humanas se excluyen del público. Cambios B–E continúan como diseño.

## 5. Proveedor/repartidor: proyección y responsabilidades

Reutilizar superficies actuales de oferta, servicios reclamados/asignación y ejecución. Ampliación aditiva de collectionInstructions conservando CONTRACT legacy; nueva fuente DeliveryShippingTerms, no valores derivados de perfil vivo. Amount/currency siempre MQ aceptada.

| Audiencia | Puede ver / hacer |
|---|---|
| Oferta a proveedor/independiente elegible | Precio/moneda, REQUESTER/RECIPIENT, CASH/PICKUP o DELIVERY, componente y aplicabilidad OFFER; no contactos privados de pagador ni evidencia de consentimiento |
| PROVIDER_ADMIN titular del servicio | Instrucción vigente, contacto operativo necesario, evidencia declarada si se aprueba; asignar y reportar incidencias según permisos actuales, no avanzar ni entregar detallado ni declarar dinero como Driver |
| Driver vigente (flotilla/independiente) | Contacto operativo de su asignación, importe y lugar/momento de cobro, estado de declaración; permisos de hitos actuales, no acceso general por tener DRIVER |
| Driver anterior tras transferencia | No escritura ni contacto vigente del receptor; sólo historial propio ya permitido. No volver a cobrar |
| SUPER_ADMIN | Audita configuración/términos/declaraciones y resuelve custodia excepcional; no suplantar al ejecutor ni editar cobros históricos |
| Propietario directo/B2B | Su snapshot y evidencia resumida, no identidad interna/actor privado ni información de otro propietario |

Propuesta de texto: “Cobrar únicamente envío: $25.00 MXN en efectivo al solicitante o su representante, en recogida”. No indicar “cobrar mercancía” desde esta instrucción. Si cancelado/devuelto/terminado: HISTORICAL y ninguna acción actual de cobro. Si transferencia con pago previamente declarado: mostrar “Envío con cobro ya declarado; no volver a cobrar”.

**Contrato opcional recomendado de declaración, sujeto a negocio:** POST `/driver/dispatches/:dispatchId/shipping-collection` con `{assignmentId,expectedRevision,quotePublicId,termsVersion,amount,currency,receivedFrom:REQUESTER|AUTHORIZED_REPRESENTATIVE,occurredAt}` y Idempotency-Key UUID como comandos DRIVER actuales;200 declaración durable. Amount/moneda deben ser eco exacto, no monto libre. Proponer extensión de GET `/driver/dispatches/:dispatchId/assignments/:assignmentId/attempt?operation=COLLECT_SHIPPING` y POST de la misma ruta `/attempt/close?operation=COLLECT_SHIPPING`, con Idempotency-Key UUID y actor original. Respuesta200 del patrón existente: APPLIED, PENDING_OR_UNKNOWN o CLOSED_NO_EFFECTS y canStartNewAttempt; la operación COLLECT_SHIPPING NO existe hoy. Cierre con confirmación explícita, sin body monetario; no borra declaración ni devuelve efectivo.409 por custodio anterior, declaración previa distinta, intento cerrado o revisión desactualizada. Se conserva la plantilla de reconciliación APP vigente; esta extensión requiere guard, enum, persistencia y pruebas nuevas. No reemplazar rutas actuales en frontend por este borrador.

No añadir cobro automático al hito, delivery.completed o terminalOutcome. No condiciona legacy/RECIPIENT sin decisión explícita; el control PICKED_UP por efectivo aplica sólo a REQUESTER nuevo si se aprueba la barrera del diseño. Futura app DRIVER deberá integrar recuperación de esta cuarta operación; no inventar UI móvil V1.19 en V1.17.

## 6. WEB / APP cliente: navegación recomendada

1. Registro PERSONAL/BUSINESS → verificar correo → login. Cuenta con otro rol: login existente y anexar perfil; no crear segunda contraseña para mismo email ni sustituir rol.
2. Inicio: capacidades, solicitud activa PERSONAL o lista BUSINESS. Avisar que el cupo se verifica al enviar, no prometer reserva desde pantalla.
3. Cotizar: recogida/destino y mercancía; pagador bloqueado REQUESTER para PERSONAL, selector explícito BUSINESS. Mismos precios por canal.
4. Confirmar datos/contactos del solicitante y representante; mostrar precio, TTL, pagador, efectivo y momento. Conversión crea MDR/MQ y ocupa cupo; aceptación final de MQ exacta publica despacho.
5. Seguimiento: fotografía con publicVersion, acciones actuales y estado de frescura; no timeline ni GPS. Polling centralizado B2B actual no se convierte en garantía de carga móvil. Revisar límites antes de definir frecuencia humana.
6. Cancelación/abandono: mostrar resultado confirmado y restricciones por custodia. Reintentos conservan clave/marker mínimo (owner, operación, key y referencia pública), sin bodies/tokens. Cambio de usuario no expone marcador de otro ni desbloquea intención pendiente.
7. Historial: términos y resultado logístico; evidencia de cobro sólo si existe declaración. No dar por pagado porque termine delivery.

Pantalla admin B2B: configuración de pagador con revisión, aviso “Sólo nuevas solicitudes; precotizaciones anteriores pueden requerir renovación”, confirmación al pasar a REQUESTER y advertencia de compatibilidad del integrador. Historial auditable, sin edición de MDR ya creadas.

## 7. Disponibilidad y criterios de entrega

Actual: login/invitación humanos, B2B MPQ/MDR/MQ, execution/identity/custodia y seguimiento versionado según código. Propuesto: CustomerAccount/CUSTOMER, signup/reset, cupo, owner directo, nueva política/snapshot de pagador y eventual declaración. Ningún cliente puede consumir estas adiciones hoy.

Antes de sincronizar frontend: decisiones §11 del diseño; backend implementado y pruebas PostgreSQL/seguridad/cupo; OpenAPI humano y B2B separados generados del código; ejemplos contractuales probados; coordinado rollout sin instancias antiguas operando directos. No se autoriza despliegue ni se asigna otra versión a GPS/app Driver desde esta entrega.

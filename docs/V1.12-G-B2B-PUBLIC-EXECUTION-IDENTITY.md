# V1.12-G — B2B Public Execution Identity

## Existing Public Identity Fields

Inspección sobre QA, base `4dbc331`, paquete 1.12.0. El contrato V1.12-A publicaba únicamente `execution.mode`. `DeliveryProvider.name` ya está documentado en el DTO como nombre visible del proveedor; se reutiliza como nombre de presentación, sin duplicar ese campo. `Driver.name` es operativo, con ejemplos que incluyen apellidos: no acredita autorización de publicación. User no tiene un nombre público. IndependentDriverProfile reutiliza el Driver; no necesita otra identidad.

Se revisaron status/view, modelos, CLAIM/TAKE, assignment/reassign/release, completion, Outbox y guardas SQL, transport/retries/HMAC, worker, lease/attempts, administración de webhooks y Swagger.

## Privacy Decision

Se añade `Driver.displayName`, opcional y nullable, explícitamente destinado a publicación. Nunca se obtiene de `name`, email, username, iniciales o apellidos. No se rellenan perfiles existentes. No se exponen IDs internos, vehículos, placa, contactos, ubicaciones, datos fiscales, financieros o de membresías.

Quien configure `displayName` debe suministrar un nombre autorizado para presentación pública. El campo no verifica identidad legal ni unicidad. Al ser texto deliberadamente público, no debe contener información privada. Las respuestas se construyen mediante selección explícita y una lista de campos permitidos, incluso al leer JSON histórico.

## Public Contract

Extensión aditiva de `GET /api/v1/delivery-requests/{publicId}/status` y de `delivery.completed.data`:

```json
{
  "execution": {
    "mode": "PROVIDER",
    "provider": { "displayName": "Mensajería Centro" },
    "driver": { "displayName": "Alex" }
  }
}
```

Para independiente: `mode: INDEPENDENT`, `provider: null`, `driver: {displayName}` o null. Los siete campos de primer nivel, estados, timestamps, eventId, tipo de evento y semántica de `execution.mode` se conservan. Los consumidores deben tolerar campos adicionales.

## Provider Semantics

Mientras está ASSIGNED se muestra el nombre visible del proveedor que tiene el claim vigente, desde su candidatura CLAIMED. Sin assignment, `driver` es null. La relación interna permite resolver identidad pero no se devuelve al consumidor. No se publican candidatos OPEN ni proveedores alternativos.

## Driver Semantics

La identidad en curso proviene exclusivamente del Driver de la asignación ACTIVE. Para ambos modelos se usa el mismo campo `Driver.displayName`.

Configuración por las rutas existentes, con sus guards de SUPER_ADMIN o membership de PROVIDER_ADMIN:

```http
PATCH /api/v1/admin/providers/{providerId}/drivers/{driverId}
Content-Type: application/json

{ "displayName": "Alex" }
```

También disponible en creación y PATCH del Driver mediante las rutas del proveedor autorizado. Se recortan espacios exteriores; longitud 1–100. Omitir conserva el valor, null lo retira de lecturas en curso/futuras. La identidad de entregas finalizadas no se modifica. Las respuestas administrativas del Driver y `/driver/me` incluyen el campo para comprobarlo. No se añadieron permisos B2B de escritura ni una pantalla Web.

## Nullable Semantics

| Caso | execution | provider | driver |
|---|---|---|---|
| REQUESTED / OPEN / EXPIRED | null | — | — |
| PROVIDER claimed sin asignación | objeto PROVIDER | nombre visible | null |
| PROVIDER asignado | objeto PROVIDER | nombre visible | displayName o null |
| INDEPENDENT | objeto INDEPENDENT | null | displayName o null |
| DELIVERED posterior a G | snapshot | nombre congelado o null | nombre congelado o null |
| DELIVERED anterior sin evidencia pública | objeto con mode histórico | null | null |
| CANCELLED con antiguo claim | conserva mode histórico | null | null |

La semántica de CANCELLED conserva el mode que V1.12 ya publicaba, sin añadir atribución vigente de personas. Si nunca hubo claim, execution es null.

## Release / Reassignment

Release deja OPEN y execution null; no retiene un ejecutor vigente. Reassignment muestra exclusivamente la asignación ACTIVE, nunca REASSIGNED. `/status` usa una transacción RepeatableRead porque Prisma puede resolver relaciones con varias consultas: todas deben observar el mismo estado, incluso si otra transacción libera, reasigna o completa.

## Delivered Identity Snapshot

`Dispatch.publicExecutionSnapshot` es JSONB nullable. PostgreSQL lo genera en la transición CLAIMED → DELIVERED, leyendo en una sentencia el proveedor y Driver de la asignación COMPLETED cuyo timestamp, usuario y actor corresponden al cierre. El bloqueo de Dispatch existente serializa completion con assignment/reassign/release.

La base rechaza snapshots suministrados o modificados arbitrariamente. Las entregas antiguas permanecen null; no se inventa evidencia consultando perfiles actuales. Los cambios posteriores de nombres, cuenta o perfil no alteran `/status` de DELIVERED.

## Persistence / Migration

Migración incremental `20260928000100_b2b_public_execution_identity`:

- `Driver.displayName VARCHAR(100) NULL`, con validación CHECK.
- `Dispatch.publicExecutionSnapshot JSONB NULL`.
- Trigger de captura e inmutabilidad `Dispatch_public_execution_guard`.
- Trigger `B2bOutboxEvent_public_execution_guard` que exige igualdad con la identidad congelada.

No se modifica una migración previa, no hay reset, backfill de nombres o eventos, ni cambios económicos. Es necesario aplicar la migración antes de ejecutar esta versión del backend. Tras aplicarla, un backend anterior que intente completar sin incluir la identidad en el Outbox será rechazado: coordinar la actualización de instancias escritoras; no mantener versiones anteriores completando servicios durante una actualización gradual.

## Status / Outbox Consistency

El cierre existente sigue escribiendo assignment COMPLETED, Dispatch DELIVERED y evento dentro de una transacción. El trigger congela identidad al actualizar Dispatch; `recordDeliveryCompleted` usa `deliveryStatusView` y obtiene ese snapshot. La base rechaza un payload cuya execution difiera. Si falla Outbox, revierten también la asignación, cierre e identidad. Un reintento de completion no crea otro snapshot/evento.

## Webhook Compatibility

Transporte, firma HMAC, retry, lease, worker y attempts no cambian. Cada intento envía el payload durable existente. No consulta perfiles para reconstruir identidad. Los eventos previos a G mantienen su payload original, que puede tener únicamente `execution.mode`; ni se reescriben ni se enriquecen al reenviar. Administración V1.12-E continúa mostrando el payload congelado.

## B2B Isolation

La lectura mantiene el filtro compuesto de publicId e IntegrationClient autenticado. Otra integración recibe el mismo 404 de una solicitud inexistente. No se agregan búsquedas públicas por persona, IDs internos o proveedor. Nombres no son identificadores ni claves de autorización.

## Remaining Risks

- No hay identidad pública de Driver hasta configurarla expresamente; no hay backfill privado.
- Entregas y eventos anteriores mantienen únicamente la evidencia histórica disponible.
- Nombre visible no es identidad legal, identificador estable ni garantía de unicidad.
- Versiones escritoras antiguas son incompatibles con la nueva guarda Outbox al completar; actualizar coordinadamente. El contrato para consumidores B2B sí es aditivo.
- La validación es local. No se verificó ni se desplegó una VM o consumidor externo.
- Sin cambios de créditos, ledger, awards, refunds, pricing, routing o PaymentContext; pruebas comparan su preservación.

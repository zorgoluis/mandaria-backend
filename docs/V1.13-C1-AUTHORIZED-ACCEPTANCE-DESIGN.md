### Cuatro hechos diferentes

1. Restaurante acepta pedido: B guarda `ACCEPTED_BY_MERCHANT`, referencia y fecha.
2. Restaurante confirma pago de comida: B guarda `CONFIRMED_BY_MERCHANT`, referencia y fecha.
3. Cliente autoriza precio del envío: **no existe en B**. RECIPIENT/CASH/DELIVERY/DELIVERY_FEE describe una intención, no consentimiento.
4. Mandaria acepta técnicamente y habilita despacho: actual para legacy, bloqueado para convertidas.

Mandaria verifica principal, ownership, formato/fechas, estados y vínculos; no banco ni gesto humano. Coita conserva evidencia del consentimiento y responde por la atestación. Ningún token `quotes:accept`, pago de comida o aceptación del restaurante sustituye el tercer hecho.

## 2. Recomendación mínima

Reutilizar **POST `/delivery-quotes/:publicId/accept`**, servicio y `openDispatch`; rama por origen persistido, nunca externalReference/header/body. Mantener legacy sin body obligatorio ni nueva key y con respuesta/replay actuales. En convertidas exigir body de atestación y key; scope existente `quotes:accept` + ownership basta como permiso técnico, no prueba de consentimiento. No autoasignar permisos ni exigir scopes de conversión a quien sólo acepta.

Nuevo registro interno propuesto `AuthorizedQuoteAcceptance`: B no conserva autorización del envío ni enlace atómico de esa evidencia con Dispatch. Reutilizar idempotencia con operación `delivery_quotes.accept_authorized`, resourceType `AuthorizedQuoteAcceptance`. Sin nuevas solicitudes/cotizaciones, estado financiero, tabla de pagos o motor de precios para una aceptación.

Flag **propuesto**, no configurado: `PREQUOTE_AUTHORIZED_ACCEPT_ENABLED=false`, independiente de emisión/conversión. Sólo primeras aceptaciones; no revoca resultados comprometidos. Replay/lecturas/cancelación siguen disponibles con autorización vigente.

Descartadas: consentimiento inferido del token/pago, quitar guardas sin evidencia SQL, body opcional convertido, ruta que duplica todo el accept, renovar expiry, precio recibido como autoridad, recotizar MDR convertida, comprobantes bancarios/PII innecesarios. La verificación directa cliente–Mandaria requeriría otro protocolo; el usuario eligió atestación.

## 5. Persistencia propuesta

`AuthorizedQuoteAcceptance` append-only, sin autorización reusable PENDING:

- UUID id; `conversionId` UNIQUE, `deliveryQuoteId` UNIQUE, `deliveryRequestId`, `integrationClientId`; `dispatchId` UNIQUE preasignado; `idempotencyRecordId` UNIQUE.
- `credentialId` atribuido por servidor, nunca secreto/token. FK RESTRICT conserva historia; revocar no borra. Replay puede usar otra credencial vigente del mismo cliente.
- `authenticatedTokenExpiresAt`, sólo del JWT verificado por servidor, para comparar el límite temporal al validar el conjunto nuevo. No guardar JWT ni conceder validez por una fecha del body. PostgreSQL comprueba el instante recibido por el backend de confianza, no verifica la firma JWT; expiración de credencial y estado/scopes actuales se contrastan además con sus filas bajo lock.
- `authorizationVersion=1`, `authorizationStatus=AUTHORIZED_BY_CUSTOMER`, `authorizationReference`, `authorizedAt`; `acceptedAt` fijado por DB.
- `authorizedAmount`, `authorizedCurrency`, `authorizedExpiresAt`: eco inmutable comprobado contra MQ, no tarifa/TTL editable. Aunque derivables del snapshot inmutable, registrarlos deja explícito el tuple atestiguado; igualdad protegida SQL.

FKs compuestas para conversión/MDR/MQ/owner; FK diferida hacia Dispatch para insertar evidencia antes de apertura. Key/resourceId y resultado recíprocos. Sin ejecución A3. Referencia opaca no es key ni ID público ni se presupone única globalmente.

SQL comprueba estructura/estado, no consentimiento humano. Escritor DB capaz de falsificar la atestación completa puede fabricar evidencia coherente: no se promete protección contra credencial de integración/aplicación/DB comprometida. DDL/superusuario fuera de garantías. Impedir incluso esa fabricación exigiría rol/procedimiento restringido o prueba independiente; no afirmar que una FK lo consigue.

## 6. Atomicidad, idempotencia y concurrencia propuestas

Reutilizar `IdempotencyService.execute` y variante interna transaccional de aceptación; no llamar al accept actual que inicia otra transacción.

1. Guard verifica JWT/principal/exp/scopes; validar DTO/key y ownership antes de revelar flag o resultado ajeno. Fingerprint operación + MQ + atestación completa normalizada.
2. Replay exacto carga proyección propia aun con flag apagado, TTL vencido o cancelación posterior. Autenticación siempre vigente; no rehacer validaciones temporales de **creación**, no recrear Dispatch. Key incompatible → HTTP_409 actual.
3. Primera aceptación: insertar key; lock compartido integración y credencial, después MDR FOR UPDATE, MQ y zona FOR SHARE. Orden uniforme con operaciones administrativas debe concretarse/probarse en C2. Contexto interno de auth nuevo con credentialId/exp/scopes desde JWT validado, nunca body: principal actual necesita extensión interna acotada, sin exponer campos en proyecciones públicas.
4. Bajo locks: MDR CREATED, origen correcto, MQ OFFERED sin aceptación previa/Dispatch, hechos B coherentes, zona ACTIVE, flag C habilitado. Reloj DB después de esperas; revalidar credencial, expiración JWT/credencial y scopes efectivos.
5. Insertar registro con tiempo DB e IDs destino; MQ ACCEPTED con ese acceptedAt. `openDispatch` reutiliza elegibilidad y snapshots de créditos recibiendo ID preasignado. Sin routing/reprecio de envío. Política ausente revierte todo.
6. Constraints diferidos validan conjunto nuevo: key ↔ registro ↔ conversión ↔ MQ ↔ Dispatch, precio/moneda/expiry/fechas, owner, hechos/manifiesto y snapshots requeridos. Revalidar vigencia DB y límite temporal de autorización técnica; locks mantienen estados de principal/zona/políticas. Validación temporal JWT requiere pasar expiración verificada a contexto interno, no aceptar fecha técnica del payload como autoridad; si se persiste para chequeo final SQL, es metadata técnica del servidor, no prueba de firma verificada por PostgreSQL.
7. Commit y sólo después logs seguros de éxito; carga de respuesta recuperable. No cuerpos, referencias privadas, tokens ni mensajes SQL con parámetros en logs. Errores: status/code/requestId e IDs públicos seguros.

Flag se comprueba antes de mutar y al final en aplicación; configuración por instancia no promete interrupción global instantánea de transacciones ya en curso. No usar flag como evidencia. Suspensión/revocación que compromete antes del lock/revalidación impide aceptación; si aceptación tiene lock compartido primero, revocación espera y puede comprometer después. No deshace Dispatch autorizado. Scope removido/token vencido debe rechazarse según esa frontera; guard actual de entrada no basta para prometer serialización. Replay autentica al solicitarse; revocación posterior tiene límite normal de lectura concurrente, sin efectos operacionales.

Misma key/cuerpo: una creación, demás replay 200. Misma key con otro body/MQ/operación: HTTP_409. Distintas keys para una MQ: un ganador, perdedores 409 `QUOTE_ALREADY_AUTHORIZED`, key perdedora rollback; sin aliases ni sustitución de consentimiento. Integrador debe guardar la key original. Lecturas permiten reconciliar si pierde key, sin revelar referencias privadas.

Cancelación comparte lock MDR: cancel gana → rechazo sin registro/Dispatch; accept gana → cancel cierra OPEN/CLAIMED por flujo existente y conserva autorización/MQ histórica. Si completion ganó, DELIVERED permanece: el 200 de cancel no basta para reemplazar (§7). Carga de replay deberá ser coherente (transacción de lectura como B); no prometer que un 200 preserve estado frente a cancelación posterior. Fallo en registro, MQ, Dispatch, candidato, snapshot, key o validación final → rollback conjunto. Deadlock/timeout reconocidos → 503 reintentable misma key; no retry infinito ni mapear cualquier fallo SQL/P2002 a replay.

**Límite temporal explícito:** reloj DB y constraints diferidos en HTTP C; no SET CONSTRAINTS IMMEDIATE. SQL directo puede adelantar evaluación temporal y comprometer tarde, igual que el límite B. No prometer instante físico de COMMIT anterior a expiry. Deben conservarse estructura autorizada completa, precio/expiry inmutables y tiempo validado. Exigir una garantía mayor sería cambio arquitectónico adicional.

## 7. Vigencia y cambios de precio

| Situación | Secuencia recomendada |
|---|---|
| MPQ vigente al confirmar transferencia/pedido | Convertir con hechos B; mostrar MQ y obtener consentimiento exacto; aceptar vigente. No despacho mientras espera pago/consentimiento. |
| MPQ vence antes de convertir | PREQUOTE_EXPIRED; nueva emisión/key y conversión. Referencias de comida pagada pueden mantenerse si siguen siendo verdaderas: no exigir segundo pago de comida. |
| MQ vence después de convertir | QUOTE_EXPIRED, MPQ sigue CONVERTED. No POST quotes sobre MDR, no liberar MPQ/editar snapshot. Cancelar MDR y confirmar estado antes de nueva secuencia, con la barrera de confirmación de §7.1 aprobada. |
| Tarifa reemplazada/inactiva | MQ vigente conserva precio/referencias/expiry. Accept no consulta tarifa de envío; nueva MPQ sí usa configuración actual. |
| Zona INACTIVE o falta política de créditos | Primera aceptación rechazada sin efectos; replay comprometido no reabre/revalida condiciones de creación. No confundir precio envío con costo de créditos. |
| Nueva Quote más cara | Nueva autorización explícita obligatoria. Nunca autoaceptar ni reutilizar consentimiento anterior. |
| Nueva Quote igual/más barata | Nuevo consentimiento también, ligado a identidad/expiry exactos. No inferir permiso de autoaceptar ahorro. |
| Cliente rechaza después de transferir | No aceptar/despachar; cancelar si hay MDR. Restaurante/integrador gestionan comida/devolución fuera de Mandaria; conservar historia. |

### 7.1 Cancelación: contrato actual y confirmación definitiva

**Admisible actualmente, por inspección de código/SQL:** POST `/delivery-requests/:publicId/cancel`, scope `deliveries:cancel`, body `{"reason":"Cotización de envío vencida; reiniciar secuencia"}` (string trim 1–500), devuelve 200 `DeliveryRequestResponse`. No exige MQ vigente ni excluye origen convertido. Bajo lock MDR cambia CREATED→CANCELLED, expira una MQ OFFERED vencida (o cancela si aún vigente) y cierra Dispatch OPEN/CLAIMED en la misma transacción. Una MQ ya EXPIRED se conserva; ACCEPTED también se conserva como historia. Las guardas B permiten cancelar MDR y expirar MQ; los constraints de construcción B no vuelven a exigir CREATED/OFFERED al cancelar. Repetir conserva razón/fecha originales, sin nueva key obligatoria. Cancelar no libera la MPQ ni permite otra conversión de ella.

Fuentes adicionales: [estado público](../src/deliveries/delivery-status.ts), [completion](../src/deliveries/delivery-completion.ts), [transiciones terminales SQL](../prisma/migrations/20260923001600_delivery_completion_rules/migration.sql). GET estado usa lectura RepeatableRead en el servicio de solicitudes. Dispatch prevalece sobre MDR: **MDR CANCELLED puede coexistir con estado logístico DELIVERED**. El cancel actual no rechaza ese caso ni revierte la entrega. La descripción OpenAPI de cancel no explica esta diferencia; C debe documentarla y probarla, sin cambiar el comportamiento legacy.

Barrera obligatoria en Coita antes de emitir el reemplazo:

1. Detener duraderamente nuevas acciones del intento anterior para ese pedido. Conservar MDR/MQ/MPQ, keys y resultados conocidos; reconciliar cualquier emisión/conversión anterior incierta, no sólo accept.
2. Cancelar la MDR identificada. Confirmar su `publicId` exacto, `status=CANCELLED` y `cancelledAt` no nulo mediante el 200 de cancel o un GET propio `/delivery-requests/:publicId` posterior. No basta que el transporte haya terminado ni recibir un error.
3. **Después** obtener un GET propio fresco `/delivery-requests/:publicId/status` con `deliveries:read`: mismo publicId, `status` CANCELLED o EXPIRED y `deliveredAt=null`. No exigir `execution=null`: puede conservar modo de una adjudicación anterior. EXPIRED solo, sin la confirmación MDR CANCELLED, no cumple la barrera. MQ EXPIRED/ACCEPTED tampoco la cumple.
4. Guardar ambas confirmaciones y cerrar el intento anterior en Coita; comprobar pedido vigente y confirmación del restaurante antes de habilitar la nueva generación. DELIVERED bloquea el reinicio automático aunque MDR sea CANCELLED. REQUESTED/OPEN/ASSIGNED, lectura fallida, estado contradictorio o resultado desconocido mantienen el pedido en conciliación, sin nueva secuencia.

La combinación confirma cancelación persistida y ausencia de despacho operativo para **ese recurso**. No requiere lectura atómica entre backends: después de cancelar MDR no puede nacer un nuevo Dispatch de ella, y los estados terminales del Dispatch no pueden reabrirse. La primera propiedad está bloqueada absolutamente en B y **debe preservarse explícitamente en la nueva aceptación C**, incluyendo SQL directo y replays; no se acredita hoy una implementación C. La segunda existe en las guardas de lifecycle. Es autoridad logística persistida, no prueba de que un ejecutor haya recibido una instrucción física ni confirmación de cobro.

No falta una ruta nueva de cancelación para este protocolo: detalle + estado públicos permiten decidir. Falta implementar aceptación autorizada C y verificar que mantiene esta barrera. Cambio mínimo C: exigir MDR CREATED bajo el mismo lock exclusivo MDR FOR UPDATE usado por cancel/accept y en la construcción SQL autorizada, conservar estados terminales/replay sin efectos y completar documentación y pruebas de cancel/status. No añadir sustitución, enlace entre sucesores ni UNIQUE sobre externalReference.

| Escenario | Decisión y recuperación obligatoria |
|---|---|
| Cancel obtiene lock MDR antes de accept nuevo | C debe rechazar aceptación; no evidencia ni Dispatch. Confirmar ambos estados según §7.1. |
| Accept compromete antes de cancel | Cancel cierra Dispatch OPEN/CLAIMED y asignaciones, con refunds de créditos existentes si corresponde. MQ/atestación permanecen históricas; comprobar estado público. No inferir fallo de accept por un timeout. |
| Completion compite con cancel | Completion bloquea Dispatch; si entrega gana, cancel puede devolver MDR CANCELLED pero GET status sigue DELIVERED: no reemplazar. Si cancel cierra Dispatch primero, completion debe rechazarlo por no CLAIMED. Probar ambas ordenaciones; no prometer que 200 cancel implica entrega no realizada. |
| Respuesta de cancel perdida / 5xx después de commit | GET MDR + status; si aún CREATED, reintentar cancel sobre **la misma MDR** y razón. CANCELLED es replay por estado, no libera MPQ. Si no se logra confirmar, detener reemplazo y conciliar; retry acotado con espera. |
| Respuesta de accept perdida | Repetir misma key/body para recuperar historia, o cancelar la MDR conocida y reconciliarla. Nunca nueva key para averiguar si aceptó. Una respuesta/replay ACCEPTED tardía no reabre ni invalida la cancelación; consultar estado, no sobreescribir el intento vigente desde una respuesta antigua. |
| Respuesta de conversión/emisión perdida | Recuperar con key/payload originales. No crear otra MPQ/MDR mientras se desconozca el resultado que podría seguir operando. Si conversión creó MDR, aplicar cancelación confirmada antes de reemplazar. |
| 401/403/404/429/timeout al cancelar o leer | No equivalen a cancelación; conservar intento pendiente, recuperar acceso/identidad o escalar conciliación. No generar credenciales ni forzar estados automáticamente. |
| Dos trabajadores de Coita o reintento tardío | Exclusión durable por pedido y generación; acciones pendientes de generaciones cerradas no pueden emitir/convertir/aceptar un sucesor. Webhook/respuesta tardíos actualizan sólo su intento identificado, nunca reabren el actual. |

### 7.3 Unicidad y secuencia exacta del reinicio

Mandaria garantiza conversión única por MPQ y, en C propuesto, aceptación/Dispatch únicos por MQ con evidencia atómica e idempotencia por key. **No garantiza una única MDR activa por pedido de Coita:** `DeliveryRequest.externalReference` tiene índice, no UNIQUE. Dos MPQ distintas y keys distintas pueden originar dos MDR para la misma referencia. Tampoco cambiar key crea una identidad empresarial nueva.

Coita debe mantener una sola generación activa por pedido mediante persistencia y exclusión entre todos sus workers/entradas (incluido flujo legacy/manual). Registrar intenciones/keys antes de enviarlas; cada reintento usa el mismo payload/key; cerrar y bloquear acciones obsoletas, y no avanzar con resultados inciertos. Esto es una dependencia externa obligatoria, **no implementada ni verificada aquí**. Si otros clientes/herramientas crean envíos para ese pedido sin esa coordinación, Mandaria no puede garantizar ausencia de duplicados entre recursos. No se resuelve inventando unicidad de externalReference.

Secuencia recomendada tras la barrera §7.1:

1. Coita confirma que el pedido sigue vigente y conserva los hechos veraces del restaurante y su pago. Reiniciar el envío **no exige otra transferencia de comida ni implica reembolso**; no sustituir sus fechas históricas por fechas ficticias nuevas.
2. Emitir nueva MPQ con nueva key persistida y condiciones físicas actuales. Precio y expiry nuevos, sin reserva. Si vence antes de convertir, terminar ese intento sin MDR y emitir otro sólo tras resolver resultados inciertos.
3. Convertir esa MPQ vigente con nueva key, condiciones coincidentes y confirmaciones válidas B. Se obtienen nueva MDR PREPAID y MQ OFFERED; snapshot y expiresAt se copian sin renovar TTL. No reusar MPQ convertida ni modificar/re-cotizar la MDR cancelada.
4. Mostrar la **MQ resultante exacta** (identidad, importe, moneda y vencimiento), separando comida ya pagada del envío al entregar. Obtener nuevo consentimiento explícito después de convertir, también para importe igual o inferior. Mostrar antes la MPQ puede informar al cliente, pero no sustituye este consentimiento ligado a MQ.
5. Coita conserva evidencia y atestigua tuple exacto con nueva key de aceptación. Mandaria C validará `MQ.createdAt <= authorizedAt <= acceptedAt DB < expiresAt`, más límite temporal final descrito en §6. Ni tiempo usado para obtener consentimiento ni reintentos amplían TTL; no basta reloj de Coita o haber iniciado HTTP antes del vencimiento.
6. Recuperar respuesta perdida con misma key/body; éxito sólo registra aceptación y habilita Dispatch, no entrega física ni cobro. Si vence después de convertir sin aceptación confirmada, reconciliar/cancelar esa MDR y repetir desde §7.1 con otro consentimiento. No bucle de renovación automático sin cliente ni dos sucesores en paralelo.

### Despliegue, desactivación y rollback futuros

Nueva migración incremental; no editar B ni inventar consentimientos por backfill. Primero esquema/guardas compatibles y flag off; después todas las instancias API/workers/lectores compatibles, luego validación de clientes/configuración y dependencia D antes de operar. Rollback seguro = flag off + conservar schema/historia y binario compatible, no downgrade destructivo/DROP/reset. Ensayo con código anterior obligatorio antes de activación.

Operación real debe esperar que ejecutores comprendan instrucciones; no suponer D implementada.

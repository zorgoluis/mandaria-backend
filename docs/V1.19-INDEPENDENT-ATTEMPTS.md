# V1.19 — Intentos independientes TAKE / RELEASE

Implementación local del 2026-10-07, sobre HEAD `b97b9d1` más cambios pendientes. No publicada, desplegada ni integrada con Android. Evidencia: [verificación](checks/v119-independent-attempts.json). No se usaron los entornos 43130/55441, 43131/55442 ni 43132/55443.

## Defectos comprobados

Antes del cambio, una consulta sin asignación no impedía que un TAKE retenido llegara después y adjudicara/cobrara. Se reprodujo con HTTP real contra Nest y PostgreSQL sintético.

También se reprodujo RELEASE con ventana de despacho vencida: HTTP 404 después de confirmar CANCELLED, EXPIRED y SERVICE_REFUND. El reloj se adelantó sólo en la prueba, conservando JWT válido. La causa era la lectura autorizada posterior al commit. Ahora la respuesta se construye dentro de la transacción; el éxito no depende de conservar acceso al despacho después de liberarlo.

## Contrato APP implementado

Prefijo `/api/v1`, autenticación humana Bearer, rol DRIVER, cuenta activa. Los recibos son propios del actor autenticado, no del dispositivo ni de un administrador. Todas estas respuestas usan `Cache-Control: no-store`.

| Método y ruta | Entrada | Respuesta 200 |
|---|---|---|
| POST `/driver/dispatches/:dispatchId/take` | `Idempotency-Key: UUID`, cuerpo `{"vehicleId":"UUID"}` | `IndependentCommandResponse` |
| POST `/driver/dispatches/:dispatchId/release` | Misma cabecera; DTO existente `{reason, reasonDetail?}` | `IndependentCommandResponse` |
| GET `/driver/dispatches/:dispatchId/independent-attempt?operation=TAKE` | Cabecera original; operación `TAKE` o `RELEASE`, sin cuerpo | `IndependentAttemptResponse` |
| POST `/driver/dispatches/:dispatchId/independent-attempt/close?operation=TAKE` | Cabecera original, operación y cuerpo vacío | `IndependentAttemptResponse` |

`ReleaseDispatchDto.reason`: `VEHICLE_ISSUE`, `PERSONAL_EMERGENCY`, `CANNOT_COMPLETE`, `OPERATIONAL_ISSUE`, `OTHER`. `reasonDetail` tiene 3–500 caracteres, se recorta y es obligatorio con OTHER. No se añade otro motivo ni ruta de ADVANCE/DELIVER. Las rutas de consulta y cierre exigen clave; TAKE/RELEASE mantienen compatibilidad sin clave descrita abajo.

Ejemplo ficticio de consulta de un RELEASE aplicado:

```json
{
  "operation": "RELEASE",
  "dispatchId": "11111111-1111-4111-8111-111111111111",
  "state": "APPLIED",
  "result": {
    "operation": "RELEASE",
    "dispatchId": "11111111-1111-4111-8111-111111111111",
    "assignmentId": "22222222-2222-4222-8222-222222222222",
    "dispatchStatus": "EXPIRED",
    "assignmentStatus": "CANCELLED",
    "credits": {
      "awardEntryId": "33333333-3333-4333-8333-333333333333",
      "refundEntryId": "44444444-4444-4444-8444-444444444444",
      "amount": 14
    }
  },
  "canPrepareNewAttempt": false
}
```

El resultado es histórico al commit. TAKE devuelve CLAIMED/ACTIVE; RELEASE OPEN o EXPIRED/CANCELLED. No es una fotografía actual. Los IDs económicos identifican exclusivamente el cargo propio y su compensación; `amount` es el movimiento entero original (negativo TAKE, positivo RELEASE, cero en adjudicación legítimamente gratuita). No es saldo actual ni dinero recibido/devuelto al cliente. `refundEntryId` es null en TAKE; un servicio legítimamente gratuito puede tener ambas referencias null.

## Recuperación sin cuerpo

Guardar antes del POST únicamente actor, operación, dispatchId y clave UUID. Tras timeout, recarga o reinicio, consultar con esa identidad y la misma sesión del actor:

- **APPLIED:** acreditar el resultado original. Una lectura actual del despacho puede responder 404 tras RELEASE u otro ejecutor; no invalida el recibo. No repetir operaciones físicas ni interpretar el estado histórico como actual.
- **PENDING_OR_UNKNOWN:** no acredita fracaso. Conservar bloqueo. Consultar o solicitar cierre técnico explícito con confirmación.
- **CLOSED_NO_EFFECTS:** la petición con esa identidad no podrá aplicar después. Permite preparar otro intento manual, sujeto a elegibilidad actual; nunca enviarlo automáticamente.

Un timeout del cierre requiere nueva consulta de la misma identidad; no asumir cierre. GET no escribe, cancela ni prolonga nada. Cerrar un intento técnico no libera una asignación, no devuelve créditos/efectivo y no acredita que no hubo una entrega física. Si el comando ganó, el cierre devuelve APPLIED.

Repetir un POST aplicado con cuerpo idéntico devuelve el resultado original. Cambiar términos con la misma clave da 409 `IDEMPOTENCY_KEY_REUSED`. Una clave cerrada da 409 `INDEPENDENT_ATTEMPT_CLOSED`. El cuerpo original no hace falta para GET/cierre. Un error del comando con rollback sigue siendo desconocido hasta cerrar: una petición concurrente o retrasada podría llegar después.

Cada actor ve sólo sus recibos. Otro DRIVER obtiene estado desconocido para su propia identidad, nunca el resultado ajeno; cambiar de cuenta no resuelve el intento anterior. No se requiere conservar acceso actual al despacho ni perfil independiente APPROVED para consultar/cerrar un recibo propio. Sí se exige sesión DRIVER activa y perfil Driver existente. Un cierre de UUID desconocido crea sólo una barrera opaca, no acceso ni reserva operacional; no revela si el despacho existe.

## Coordinación y límites

Migración incremental `20261007000300_independent_dispatch_attempts` crea `IndependentDispatchAttempt`, identidad primaria actor/dispatch/operación/clave, recibo inmutable y barrera de cierre. Dispatch es un identificador opaco sin FK para que cerrar un UUID desconocido no sea un oráculo de existencia. Usuario tiene FK restrictiva. No se guarda el cuerpo: sólo hash y resultado seguro.

Comando con clave y cierre adquieren el mismo advisory lock transaccional antes de resolver el recibo. Asignación, award/refund y recibo se confirman o revierten juntos. El cierre que gana bloquea el POST tardío; si gana el comando, se conserva su resultado. Locks operativos existentes coordinan candidatos, recursos, custodia y créditos. Reiniciar procesos no borra recibos.

**Llamadas antiguas sin clave:** siguen devolviendo `DriverDispatchResponse`, sin recibo ni protección de este protocolo. Un cierre no puede invalidar un escritor sin clave o una instancia anterior que ignore la cabecera. No se reconstruyen recibos históricos a partir del estado actual ni del saldo. APP debe usar siempre clave y las rutas explícitas nuevas; no inferir capacidad por ausencia de campos o por error HTTP.

## Elegibilidad y RELEASE

- TAKE exige Driver ACTIVE/usuario activo, capacidad independiente APPROVED, vehículo propio ACTIVE y ambos libres considerando todas las asignaciones ACTIVE, incluidas las de flotilla. Coverage/tipo/ventana, saldo y unicidad conservan sus validaciones. ACTIVE no significa libre; `canTakeServices` es orientativo, el POST revalida bajo locks.
- `availability` no es un nuevo requisito de TAKE en este cambio. La capacidad independiente es distinta de la pertenencia a flotilla; no se amplían permisos de TAKE por tener rol DRIVER ni se añade un campo de capacidad.
- RELEASE con clave exige DETAILED. LEGACY devuelve 409 `INDEPENDENT_RELEASE_LEGACY_UNSUPPORTED`; APP mantiene bloqueado LEGACY/UNKNOWN. Las llamadas antiguas sin clave conservan su comportamiento histórico, sin atribuirles nuevas garantías ni inventar custodia. La política de liberación legacy con custodia desconocida sigue pendiente para APP.
- Tanto RELEASE con clave como sin ella rechazan incidencia abierta (`CUSTODY_INCIDENT_OPEN`), custodia desde PICKED_UP (`CUSTODY_OPERATION_FORBIDDEN`) y declaración de efectivo (`SHIPPING_COLLECTION_REQUIRES_RESOLUTION`), incluso antes de recoger. No basta ocultar botones.
- La suspensión del perfil independiente con asignación ACTIVE ya está rechazada por producto y DB. No se fabricó ese estado para probarlo. Avance y entrega conservan autorización por asignación/custodia vigente, sin introducir una nueva exigencia de aprobación comercial. La suspensión comercial no se interpreta como permiso para abandonar custodia.
- RELEASE válido compensa el cargo con SERVICE_REFUND único y `reversesEntryId` del SERVICE_AWARD original. Esto devuelve créditos del ejecutor; no devuelve efectivo al cliente. Las resoluciones excepcionales existentes se conservan.

Otros errores conservados: 400 DTO/UUID/cabecera inválidos; 401 sesión; 403 rol; 404 recursos no autorizados; 409 `INDEPENDENT_NOT_APPROVED`, `DRIVER_NOT_ELIGIBLE`, `VEHICLE_NOT_ELIGIBLE`, `DRIVER_BUSY`, `VEHICLE_BUSY`, `TAKE_CONFLICT`, `INSUFFICIENT_CREDITS` y conflictos operacionales existentes. 429 aplica según límites existentes. Un 5xx/timeout no autoriza repetir con otra clave: reconciliar.

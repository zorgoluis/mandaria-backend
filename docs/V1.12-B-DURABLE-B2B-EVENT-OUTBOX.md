# V1.12-B — Durable B2B Event Outbox

Cuando una entrega llega a `DELIVERED`, Mandaria registra el hecho de forma durable y atómica.
V1.12-B **no** entrega nada por HTTP.

```text
V1.12-A  el cliente B2B puede observar el estado de su entrega
V1.12-B  delivery.completed queda registrado de forma durable
V1.12-C  entrega del evento por webhook (futuro)
```

## 1. Qué existía antes

La inspección del backend real encontró: ninguna tabla de eventos, ningún outbox, ningún inbox y
ningún mecanismo de publicación. `ApiIdempotencyRecord` guarda huellas de peticiones, no eventos, y
el único JSON persistido del sistema era la geometría de `ServiceZone`. La «señal de auditoría» de
V1.11-A era una línea de log estructurada (`DELIVERY_COMPLETED`), que es interna y efímera.

Sí existía lo necesario para no inventar nada nuevo: la transacción de V1.11-A
(`src/deliveries/delivery-completion.ts`), el modelo público de V1.12-A
(`src/deliveries/delivery-status.ts`), la relación `IntegrationClient → DeliveryRequest → Dispatch`,
y una filosofía consolidada de tablas inmutables (CreditLedgerEntry, DispatchCreditSnapshot,
DispatchPreEnforcementAward) con sus guards y su interruptor de purga sólo para bases `*_test`.

## 2. El flujo

```text
Proveedor / Independiente
        │ DELIVER
        ▼
┌──────────── una transacción PostgreSQL ─────────────┐
│ DeliveryAssignment   ACTIVE   → COMPLETED           │
│ Dispatch             CLAIMED  → DELIVERED           │
│ B2bOutboxEvent       delivery.completed             │
└──────────────────── COMMIT ─────────────────────────┘
```

`DELIVERED` + evento, o ninguno de los dos. Nunca una entrega nueva sin su evento.

## 3. El modelo

`B2bOutboxEvent`: el sobre vive en columnas y la instantánea en `payload`, de modo que cada parte
tiene **una sola** representación.

| Campo | Qué es |
|---|---|
| `id` | El `eventId` que un consumidor usará para deduplicar. Nunca el id de la DeliveryRequest: son conceptos distintos y una solicitud puede producir varios eventos. |
| `type` | Enum `B2bEventType`, hoy sólo `DELIVERY_COMPLETED`. El nombre público `delivery.completed` vive en un único lugar del código. |
| `integrationClientId` | El dueño: el cliente que creó la solicitud. |
| `deliveryRequestId` | El sujeto, siempre presente. |
| `dispatchId` | El servicio. Obligatorio para `DELIVERY_COMPLETED`; opcional para eventos futuros anteriores a la publicación de un servicio. |
| `occurredAt` | Cuándo ocurrió el hecho, **no** cuándo se escribió la fila. |
| `payload` | La instantánea congelada del contrato público de V1.12-A. |
| `recordedAt` | Cuándo se escribió la fila. |

## 4. El evento

```json
{
  "eventId": "5f2c…",
  "type": "delivery.completed",
  "occurredAt": "2026-09-24T09:47:12.345Z",
  "data": {
    "publicId": "MDR-000123",
    "externalReference": "ORDER-4711",
    "status": "DELIVERED",
    "execution": { "mode": "PROVIDER" },
    "requestedAt": "2026-09-24T09:00:00.000Z",
    "deliveredAt": "2026-09-24T09:47:12.345Z",
    "cancelledAt": null
  }
}
```

`data` es exactamente lo que responde `GET /delivery-requests/{publicId}/status` en ese instante, y
se construye con la **misma y única** función `deliveryStatusView`: no hay un segundo mapeo que
pueda divergir. Una prueba compara la instantánea persistida con el cuerpo HTTP y exige igualdad.

`externalReference` se conserva con la semántica que ya tenía: texto opaco del cliente, sin
interpretar.

## 5. Por qué una instantánea y no una reconstrucción

```text
el hecho ocurre en T1 → los datos cambian en T2 → el webhook sale en T3
```

El receptor debe recibir T1. Por eso el payload se congela al ocurrir el hecho y **no** se recalcula
cuando V1.12-C lo entregue. Una prueba cancela la DeliveryRequest después de la entrega —un cambio
legítimo que sí modifica la fila— y comprueba que el payload no se mueve.

## 6. Lo que el payload nunca contiene

Ni ids internos (`dispatchId`, `deliveryRequestId`, `integrationClientId`), ni `providerId`,
`driverId`, `vehicleId` o `deliveredByUserId`, ni créditos, ledger, políticas, snapshots, contexto
de pago, credenciales o secretos. No es un volcado de Prisma: es el contrato público deliberado, y
**PostgreSQL lo exige**: la función `b2b_delivery_completed_payload_ok` obliga a exactamente las
siete claves públicas, prohíbe las internas y exige que la instantánea diga `DELIVERED`.

Ampliar el contrato público requiere por tanto una migración. Es deliberado: es una promesa
versionada a sistemas externos.

## 7. Garantías

**De la aplicación:** atomicidad. El evento se escribe dentro de la transacción de V1.11-A, con el
mismo `deliveredAt` —el reloj se lee una vez y se pasa, no se vuelve a consultar—.

**De PostgreSQL:**

| Garantía | Cómo |
|---|---|
| Un `delivery.completed` por entrega | Índice único parcial `B2bOutboxEvent_delivery_completed_key ON ("dispatchId") WHERE type = 'DELIVERY_COMPLETED'` |
| El dueño es quien creó la solicitud | FK compuesta `(deliveryRequestId, integrationClientId) → DeliveryRequest(id, integrationClientId)` |
| El servicio pertenece a la solicitud | FK compuesta `(dispatchId, deliveryRequestId) → Dispatch(id, deliveryRequestId)` |
| El evento sólo lo escribe quien entrega | `b2b_outbox_event_guard` compara el `xmin` del Dispatch con la transacción actual, igual que hace el guard de snapshots de V1.10-C |
| `occurredAt` es el `deliveredAt` del payload | CHECK `(("payload"->>'deliveredAt')::timestamptz AT TIME ZONE 'UTC') = "occurredAt"` |
| Inmutable e imborrable | `b2b_outbox_event_guard` (UPDATE y DELETE) y `B2bOutboxEvent_no_truncate` |
| Ninguna entrega nueva sin evento | Constraint trigger diferido `Dispatch_b2b_delivery_completed_required`, comprobado al COMMIT |

La elección del índice único merece justificación: la clave es el **Dispatch**, no la
DeliveryRequest ni el par `(entidad, tipo)`. V1.12-A confirmó que hay como máximo un Dispatch por
DeliveryRequest, así que «uno por Dispatch» es «uno por entrega lógica». Y se hace con un índice
**parcial por tipo** porque la mayoría de los eventos futuros se repiten legítimamente: un servicio
puede reclamarse y liberarse muchas veces. Añadir `delivery.released` mañana no exige rediseñar
nada ni siquiera crear un índice.

## 8. La frontera, sin columna nueva

`Dispatch_b2b_delivery_completed_required` es un trigger sobre la **transición** a `DELIVERED`:

```sql
AFTER UPDATE ON "Dispatch" ... WHEN (NEW.status = 'DELIVERED' AND OLD.status IS DISTINCT FROM 'DELIVERED')
```

Sólo puede ver entregas completadas a partir de ahora. Las que ya estaban `DELIVERED` nunca vuelven
a transicionar —`dispatch_guard` prohíbe modificar un dispatch resuelto— así que quedan fuera de la
regla **por construcción**, sin bandera, sin backfill y sin la ambigüedad que la frontera V1.10-C/D
necesitó resolver con una columna. Un `Dispatch` tampoco puede nacer `DELIVERED`: el guard exige
`OPEN` al insertar.

Al aplicar la migración, `mandaria_db` tenía 22 entregas históricas `DELIVERED`. Siguen sin evento,
siguen siendo legítimas y siguen observándose por `GET /delivery-requests/{publicId}/status`.

## 9. Idempotencia

Repetir `/deliver` devuelve 200 sin escribir, como en V1.11-A, y por tanto **sin un segundo
evento**. La garantía no depende de un `if` en la aplicación: aunque algo escribiera dos veces, el
índice único parcial lo impide. Diez entregas simultáneas producen una transición y un evento, en
ambos modelos de ejecución.

## 10. Lo que V1.12-B no hace

Sin webhook, sin URL configurable, sin worker, sin scheduler, sin reintentos, sin backoff, sin
intentos de entrega, sin HMAC, sin secreto de webhook, sin `SENT`/`FAILED`/`PROCESSING`, sin
`nextAttemptAt`, sin dead-letter, sin WebSocket ni push. **Tampoco estados de transporte**: la
existencia de la fila *es* el hecho; V1.12-C/D decidirán el modelo de entrega.

Sin API de lectura (`GET /events`, `GET /outbox`) y sin administración del Outbox: es infraestructura
interna. La observabilidad externa sigue siendo V1.12-A. El contrato público y `docs/openapi.json`
no cambian.

Crear el evento no cobra ni devuelve créditos, no toca saldos, `SERVICE_AWARD`, `SERVICE_REFUND`,
snapshots ni `CreditPolicy`; no recalcula rutas ni distancias, y no modifica el contexto de pago.

## 11. Limitaciones conocidas

- **Nadie lee el Outbox todavía.** Los eventos se acumulan sin consumidor hasta V1.12-C. No hay
  retención ni purga: una fila nunca se borra por el camino normal.
- **Un solo tipo de evento.** `delivery.completed` y nada más. `delivery.requested`, `.opened`,
  `.claimed`, `.assigned`, `.released`, `.cancelled` y `.expired` no existen aún, deliberadamente.
- **Sólo entregas nuevas.** Las anteriores a la frontera no tienen evento y no lo tendrán: fabricar
  un `occurredAt` para un hecho antiguo sería inventar historia.
- **El contrato del payload está clavado en SQL.** Añadir un campo público exige migración.
- **`recordedAt` depende del valor que envía Prisma.** Su `DEFAULT CURRENT_TIMESTAMP` —el mismo que
  usa todo `@default(now())` del proyecto— escribe la hora **local** del servidor, mientras el resto
  de la columna es UTC. Hoy no hay discrepancia porque Prisma suministra el valor; un `INSERT` por
  SQL crudo que lo omita guardará una hora desplazada. Ninguna garantía de V1.12-B depende de
  `recordedAt`, precisamente por eso.

## Decisión previa de construcción SQL

Se descarta xmin/XID: xmin es un identificador de 32 bits, puede pertenecer a una subtransacción y su interpretación cambia con wraparound/freeze. Igualar identificadores truncados no prueba autorización para construir y ninguna vuelta completa se ha ensayado aquí.

Se conserva el origen insertado primero y las FKs diferidas de B1. Se agregan a la conversión tres campos de manifiesto inmutable: stopIds UUID[], packageIds UUID[] y financialContextId UUID. Son identidad de los hijos autorizados, no copia de condiciones, precio ni estado. Las listas contienen exactamente los IDs que deben existir al commit, sin duplicados. Un trigger sólo permite INSERT de esos IDs para esa MDR; UPDATE/DELETE/reparentado quedan prohibidos. Una comprobación diferida exige que el conjunto completo coincida con el manifiesto. Después del commit todos esos IDs están ocupados por PKs y no se pueden eliminar: es imposible agregar otro hijo autorizado. Funciona también con SET CONSTRAINTS IMMEDIATE, savepoints y transacciones posteriores; no hay autorización temporal ni bypass. No depende de XID, freeze ni privilegios de despliegue nuevos. Los DDL/superusuarios capaces de desactivar triggers quedan fuera de la garantía, igual que las guardas existentes.

Esta ampliación mínima de identidad respecto de B1 se documenta antes de implementarse. El manifiesto no se expone en API.

## Atomicidad, locks y tiempo

Orden: unique de key/owner → MPQ FOR UPDATE → ServiceZone FOR SHARE → reloj DB posterior a locks → comparación/confirmaciones → conversión con manifiesto → MDR/hijos/MQ → constraints diferidas → commit → load coherente RepeatableRead. El trigger repite las verificaciones de key/owner/zona y fija convertedAt UTC con precisión milisegundos. La constraint final comprueba vigencia, snapshot, condiciones canónicas desde hijos, manifiesto completo y resultado idempotente mutuo. Los hijos no dependen de identidad de transacción, por lo que forzar constraints inmediatas no abre una ventana para agregarlos.

Dos keys sobre MPQ serializan; una gana, otras hacen rollback sin key huérfana. Misma key/body recupera winner por unicidad existente. Body/operación/publicId diferente entra en conflicto. Respuesta perdida después de commit se recupera sin duplicar. Replay requiere autenticación/scopes actuales y no recrea ni consulta precio, vigencia o zona para autorizar de nuevo. Autenticación inicial no promete atomicidad con una revocación posterior, igual que los endpoints existentes.

No nuevo TTL. MQ.createdAt y MDR.createdAt/requestedAt son convertedAt, MQ.expiresAt es MPQ.expiresAt. Vigencia se comprueba antes de construir y al final por constraint diferida. No se afirma controlar el instante físico del commit ni el envío de la respuesta. Un escritor SQL que fuerza SET CONSTRAINTS IMMEDIATE adelanta la evaluación temporal: no prolonga expiresAt ni puede despachar; el servicio nunca lo hace. B3 debe revisar expresamente ese límite temporal y el comportamiento de aislamiento/contención. La garantía de conjunto íntegro/manifiesto no depende de cuándo se fuerza la constraint.

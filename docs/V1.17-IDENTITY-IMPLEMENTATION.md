## Modelo y autorización

- `CustomerAccount`: perfil 1:1 de User, PERSONAL/BUSINESS, `active`, nombres, revisión y fechas. No crea IntegrationClient ni DeliveryProvider.
- `CustomerChallenge`: hash de token aleatorio de un solo uso, propósito REGISTER/VERIFY/RESET, vencimiento y consumo. Nunca almacena token en claro en PostgreSQL. El transporte de correo privado necesariamente contiene el enlace; no registrar/enviar ese enlace a herramientas de analítica.
- Alta nueva crea User CUSTOMER sólo al verificar correo y elegir contraseña. No crea cuentas antes de confirmar ni concede roles operativos.
- Anexión a una cuenta existente conserva su rol y sesiones; requiere User activo y correo verificado. Perfil propio exige también CustomerAccount activo. No se expone selector de otro usuario.
- El estado del perfil usa `active` siguiendo User, en lugar del enum ACTIVE/SUSPENDED inicialmente propuesto. Cambiar tipo y capacidades de cupo todavía no están implementados; DTO rechaza esos campos.
- JWT nuevos incluyen `sv`. Tokens antiguos sin ese campo equivalen a versión 0, valor inicial de las cuentas existentes. Reset incrementa versión y revoca refresh en la misma transacción; AccessGuard compara la versión persistida. Login/refresh y reset se serializan sobre User. Logout conserva su comportamiento anterior: revoca el refresh indicado.

## Contrato real para WEB y futura APP

Base `/api/v1`; esquemas humanos en `docs/openapi.json`, excluidos de `docs/openapi-b2b.json`. No hay interfaz implementada ni disponibilidad acreditada en QA remoto/producción.

| Método / ruta | Entrada | Resultado |
|---|---|---|
| POST `/customer-registration` | `{email,type,displayName,businessName?}` |202 `{status:"ACCEPTED"}` genérico. Envía correo si procede |
| POST `/customer-registration/resend` | **Mismo perfil completo que registro**, no sólo email |202; reemplaza desafío pendiente |
| POST `/customer-registration/confirm` | `{token,password}` |201 `{status:"CONFIRMED"}`; después login normal |
| POST `/auth/password-recovery` | `{email}` |202 genérico para existente/inexistente/inactivo |
| POST `/auth/password-reset` | `{token,password}` |200 `{status:"CONFIRMED"}`; requiere login nuevo |
| POST `/customer/contact-verification` | Sin body; JWT humano |202; envía al email de la cuenta autenticada |
| POST `/customer/contact-verification/confirm` | `{token}` + JWT humano |200 CONFIRMED; token debe pertenecer al correo propio |
| POST `/customer/profile` | `{type,displayName,businessName?}` + JWT humano |201 perfil; cuenta activa y verificada, anexión única |
| GET `/customer/profile` | JWT humano |200 perfil propio activo |
| PATCH `/customer/profile` | `{expectedRevision,displayName?,businessName?}` + JWT humano |200 perfil y revisión incrementada; conflicto no sobrescribe |

Ejemplo ficticio de respuesta GET/PATCH:

```json
{"type":"PERSONAL","displayName":"Cliente de ejemplo","businessName":null,"revision":1,"active":true}
```

Email se normaliza a minúsculas/trim; type PERSONAL/BUSINESS; displayName 1–100, businessName opcional 1–160; password 16–128; token 32–200 caracteres; revisión entera >=1. Campos desconocidos rechazados. Las rutas de registro/recuperación y verificación tienen cinco peticiones/minuto por IP y operación; resto usa el límite general existente.

Errores reales: 400 validación/ACCESS_TOKEN_INVALID; 410 ACCESS_TOKEN_EXPIRED; 401 JWT/sesión/cuenta inactiva; 403 CUSTOMER_CONTACT_NOT_VERIFIED o CUSTOMER_ACCESS_DENIED; 409 PROFILE_ALREADY_EXISTS o PROFILE_REVISION_CONFLICT; 429 límite; 503 CUSTOMER_ADMISSION_DISABLED para registro/confirmación/anexión. Envelope/correlación actuales; respuesta genérica de solicitud de correo no acredita entrega del mensaje. Fallo de transporte registra únicamente CUSTOMER_ACCESS_MAIL_FAILED.

Enlace propuesto para la interfaz: `MANDARIA_WEB_URL` + `/customer/access`, con fragmento `token`/`purpose`. La interfaz todavía debe construirse; leer el fragmento, retirarlo de la barra y evitar persistirlo/loguearlo. REGISTER pide contraseña y confirma registro; RESET confirma nueva contraseña; VERIFY requiere sesión del mismo usuario. Nunca enviar token a rutas B2B.

Respuesta perdida: registro/confirmación no recrea perfiles; token consumido devuelve 400. Intentar login con la contraseña elegida permite acreditar una confirmación previa; si no es posible, solicitar recuperación. No interpretar token inválido como prueba de que la cuenta no existe. PATCH perdido: consultar perfil/revisión antes de otra modificación. Esto no sustituye los recibos logísticos pendientes en B–E.
